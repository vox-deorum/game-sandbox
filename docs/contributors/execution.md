# The execution boundary

A live session straddles the container boundary: a sandboxed container runs the Python harness and the game, and the Node backend supervises it and relays its state to the browser. This page describes that seam — the execution-driver interface, the sandbox profile, the transport between container and backend, the WebSocket protocol between backend and browser, the live runner inside the container, and how a second driver slots in. The design rationale lives in the [execution spec](../../specs/execution.md) and the [interaction spec](../../specs/interaction.md); this page is how it is built.

## The execution driver interface

`driver/index.ts` is the seam, and it holds types only — no implementation and, deliberately, no `dockerode`. An `ExecutionDriver` has two methods: `ensureImage(spec)` builds or fetches an image and returns a launch-ready ref, and `launch(spec)` starts one session container and returns a `SessionProcess`. Everything a running session needs hangs off that process: its line channel out (`output`), a `send` for lines in, a `diagnostics` stream for the logger, an `exited` promise carrying the exit code and a driver-neutral `oomKilled` flag, and a `kill(graceMs)` backstop.

The bidirectional channel is part of the abstraction, not something the layer above selects: the interface promises an ordered, newline-delimited, bidirectional UTF-8 text channel and says nothing about how it is carried. The local Docker driver carries it over attached stdio; a Kubernetes driver may use attach, exec, or a sidecar. Nothing above the interface may assume stdio, file descriptors, or ports.

## The sandbox profile

`SandboxProfile` expresses the sandbox in driver-neutral terms, and each driver maps it onto its platform: `cpus`, `memoryMb`, `readOnlyRoot` (always true), a `scratch` writable tmpfs (`containerPath` plus `sizeMb`), `network` (`none` in this stage; the gateway-only value arrives in Stage 7), and `mounts` (the recordings volume is the one mount this stage uses). The local Docker driver maps these onto `NanoCpus`, `Memory` with `MemorySwap` set equal so swap cannot soften the quota, `ReadonlyRootfs`, `Tmpfs`, `NetworkMode`, and `Binds`, drops all capabilities, and labels the container `game-sandbox.session=<id>` for supervision. On construction the driver reaps any leftover labeled containers, so a crashed-backend restart starts clean without a supervisor.

## The session base image

One base image per dependency-set version, tagged `game-sandbox/session-base:deps-v<N>` (this stage needs only v1). Its Dockerfile (`backend/images/session-base/Dockerfile`) builds from the repo root, because the image is assembled from monorepo sources: the pinned v1 dependency set from `templates/base/requirements.txt`, then the `harness` and `environments` packages from source, then the composed `hello` example placed at `/opt/agents/builtin` as the built-in scripted agent. The entrypoint is `python -m game_sandbox_harness.live`, and the orchestrator appends the session config as a single JSON argv element. The built-in agent lets watch-style sessions exercise the real submission load path before any submission exists, and Stage 5 overlays submission code on top of an image like this one. Whether the driver rebuilds or reuses an existing tag is driver configuration (`imagePolicy`), not caller policy. The backend builds the image lazily on the first session and then reuses it, so a contributor who changed the Dockerfile or a bundled source rebuilds it directly with `npm run build:image`, which forces a rebuild through that same driver build path without launching a session (see [running it locally](backend.md#running-it-locally)).

## The transport: line classification and envelopes

The outbound stream from the container is JSONL, and recording lines pass through unchanged so the wire form and the stored form stay one format. One rule classifies every line in both directions: a line is an **event envelope** when its top-level object carries a `kind`, and a **recording line** (the header or a per-step state) otherwise. The rule holds because the state schema declares no top-level `kind`, and a backend test asserts that against the packaged schema so it cannot rot silently.

This stage defines one outbound envelope kind, `result`, emitted once at session end with the episode outcome (ticks, scores, termination reason, step-timeout counts, recording id); it is never written to the recording. Inbound command envelopes — backend to container, over the driver channel — carry a `kind`, a slot id where applicable, and a payload: `{"kind":"input","slot":"player_0","action":<json>}`, `{"kind":"pause"}`, `{"kind":"resume"}`, and `{"kind":"stop"}` for a graceful end. Stage 9 adds `chat` on the same shape. Unknown kinds and malformed lines are logged and ignored — the container must never die because a client sent garbage.

## The WebSocket protocol

The backend-to-browser protocol uses the same split. Server-to-client frames are the header and state lines relayed verbatim, the relayed `result` envelope, relayed `pause`/`resume` echoes so every attached client can show the paused state, and one backend-originated frame, `{"kind":"session","status":"running"|"ended","reason"?}`. On attach the backend immediately sends the buffered header, the most recent state, and the current status, so a renderer can draw without waiting for the next step; full catch-up and scrubbing belong to the Stage 4 replay viewer. Client-to-server frames are the same command envelopes as the container side. The backend validates the envelope shape and the sender's authority, then forwards — it never interprets an action, because the container is authoritative. Commands are honored only from the session owner, `input` only in human mode and only for a slot the environment exposes; a socket whose backlog crosses a threshold is dropped rather than letting one slow client stall the relay. Slot ids ride every input, so later multi-human sessions need no new transport. Because a browser cannot set a header on a WebSocket upgrade, the socket client carries the acting user as a `user` query parameter; `resolveUserId` reads the header first and that parameter second, so identity stays one function for both fetch and upgrade.

## The orchestrator and teardown

`session/orchestrator.ts` owns the lifecycle above the driver. Starting a session validates the environment and mode against the generated metadata (a 400), checks the user against the session allowlist (a 403), and enforces one active session per user (a 409 whose body carries the active session's id for the rejoin path), then resolves the seed and the human-slot timeout (the request override, else the metadata default), ensures the image, inserts the `starting` row, and launches one container with the sandbox profile and the session-config argv. From there each session drives itself as a `LiveSession`: it consumes the container's output, buffers the header and latest state for late attachers, marks the row `running` when the header arrives, and relays everything to the attached sockets.

Every end path converges on one idempotent finalize that records the reason, tells the clients, kills the container, and clears the registry — the first caller's reason wins, so an orchestrator-chosen reason is not overwritten by the container's own `result` arriving during the kill grace. The paths are: the container ends itself (`terminated`, `truncated`, `episode_limit`, or a client `stop` → `stopped`); the idle window passes with no attached socket — or, in human mode, no inbound command (`idle_timeout`); the wall-clock backstop fires on a hung container (`time_limit`); or the container is OOM-killed or crashes (`oom_killed` / `error`).

## The live session runner (container side)

Inside the container, `python -m game_sandbox_harness.live` is the harness's live runner. It is a second thin loop over the very same `Episode.step_once` that the headless `run_episode` uses; the only realtime-versus-turn-based difference is one conditional on the environment's pace interval, which is the "one code path reading the pace interval" the [interaction spec](../../specs/interaction.md) requires.

- **Pacing.** For an environment with a pace interval (Flappy Bird, realtime) the loop waits until the next cadence instant before each step; for one with no interval (turn-based) it does not, and its external source blocks for input instead.
- **Pause.** Pausing freezes the cadence and the decision clock together: the injected `PausableClock` subtracts accumulated paused time, so every duration in the system — a step's decision budget, the next cadence instant — freezes with it, with no special case in the loop. Headless runs never construct a live loop, so they never pace and never pause.
- **The transport source.** An external (human) slot is fed by a `TransportSource` over a command pump that latches the latest input per slot. With a pace interval it returns the latched input or `None` immediately and the loop's pacing does the waiting; with none it blocks in short slices until input arrives or the human-slot timeout expires. Either way a `None` routes through the existing default action — noop for Flappy Bird — with no agent-timeout accounting.
- **Stdout hygiene and the tee.** The runner claims the real stdout for the protocol before any game import (PyGame prints a banner), so stray prints land in diagnostics. Every serialized line is written to the recording on the mounted volume and mirrored onto the protocol stream by the same writer, so the streamed bytes and the stored bytes are identical by construction.

## Adding a driver

A second driver — the Kubernetes driver is the planned one — is a pure addition: it implements `ExecutionDriver` in a sibling folder under `driver/`, maps the same `SandboxProfile` onto its platform, and carries the line channel however it likes. Nothing above the interface changes, because the orchestrator, the relay, and the protocol depend only on `driver/index.ts`. A Biome import-isolation rule keeps that boundary honest: `dockerode`, `child_process`, and the database engine are denied across `backend/src`, re-permitted only inside their owning folders (`driver/docker/` and `storage/`), and the existing Biome CI check enforces it on every PR. Keep Docker-specific knowledge inside `driver/docker/`, and the addition stays pure.
