# Stage 5.4: Sandboxed Load Check and Overlay Build

Status: not started.

Part of [Stage 5](../stage-05-submissions.md). This is build-order step 4: the dynamic validation layer and the build pipeline. A new harness `validate` command runs the dynamic half of the loader inside the locked-down container with no environment stepping; a `submission-overlay` image spec on the Stage 3 driver overlays the fetched code onto the right base image; and the load check runs against the built overlay. This step needs Docker, so its tests are gated like the other Docker suites.

## Harness `validate` command

A new subcommand in the Python harness alongside the existing session entry point. It runs `load_agent`: import the entry-point module, instantiate the named class, confirm the instance exposes callable `reset` and `act` (the required hooks from [submission.md](../../docs/specs/submission.md); optional `learn`/`chat` are not required), and then exits with a structured result. It **never** constructs or steps the environment: this runs the agent's import and constructor exactly once, as both [submission.md](../../docs/specs/submission.md) and [execution.md](../../docs/specs/execution.md) require, and nothing more.

It reuses the dynamic half of the same loader the live session uses (`load_agent` / the manifest module), so the load check and real play agree on what "loads" means; the static half is the backend's step-3 mirror and is not re-run here. Output is a structured, parseable result: success, or a failure carrying a reason the backend turns into the owner-visible message. The initial closed set is `import_error` (the module failed to import), `class_not_found` (the manifest names a class the module does not define, the exit-criterion case), `constructor_error`, and `missing_hook` (no callable `reset`/`act`), each with the underlying Python error captured for the owner's debug view. Exit code plus a structured line on the agreed stream, classified the same way the session protocol classifies harness output (see [stage-03/transport-and-live-runner.md](../stage-03/transport-and-live-runner.md)).

## Overlay build on the driver

The build pipeline from [execution.md](../../docs/specs/execution.md): a `submission-overlay` image spec added to the execution-driver interface and implemented in the Docker driver (see [stage-03/execution-driver-and-image.md](../stage-03/execution-driver-and-image.md)). The spec carries `depsVersion`, `submissionId`, the prepared source tree path, and the slot directory to copy into. Building overlays the submitted code into `/opt/agents/submissions/<slot id>` on top of the base image for the dependency-set version the iteration pins. The source tree is the step-2 checkout for git sources or a copy of the local folder for local sources, feeding the same overlay path (per [execution.md](../../docs/specs/execution.md)). There is **no per-submission dependency installation**: dependencies come entirely from the versioned base image, so the overlay is code-only and fast. The base image per set version is the one Stage 3 already builds and keeps.

The build goes **through the Stage 3 execution driver**, never around it. Nothing above the driver assumes Docker specifics, and the build is one more driver operation expressed in driver-neutral terms. Like the git fetch (step 2's `SUBMISSION_GIT_TIMEOUT_MS`) and the load check (below), the build is **bounded by a timeout** so a hung or pathological build cannot stall the single-concurrency validation worker indefinitely; on timeout the driver tears the build down and the worker records the `build` stage as `failed` with a timeout reason, rolling the submission up to `build_failed`. The timeout is driver configuration alongside the caching policy. Caching is **driver configuration, not policy hardcoded above it**: the Docker driver tags overlay images deterministically from the configured prefix, dependency-set version, and submission id, then honors the existing `DOCKER_IMAGE_POLICY` (`reuse` or `rebuild`). That keeps the default fast for repeated watch runs while still letting development force rebuilds.

## The load check against the built overlay

After a successful build, the driver launches the overlay image running the harness `validate` command under the **same locked-down profile** real sessions use: no network, read-only filesystem except scratch, fixed CPU/memory quotas (the sandbox profile from [execution.md](../../docs/specs/execution.md)), with a **short timeout** since import-and-construct should be near-instant and a hang is itself a failure. The command validates the repo root at `/opt/agents/submissions/player_0` for this single-slot stage. The driver tears the container down regardless of outcome.

## Overlay-image eviction

Every distinct submission that reaches the build stage leaves a cached `submission-overlay` image tagged by its id, so without reclamation the daemon's disk grows one image per submission for the life of the deployment — the image analogue of the unbounded recordings Stage 4 had to evict. Stage 5 reclaims them with a sweep modeled directly on the Stage 4 retention sweep ([stage-04/replay-and-retention.md](../stage-04/replay-and-retention.md)): it runs at startup, on a configured interval, and after each successful overlay build — both the validation build here and step 6's on-demand watch-run rebuild, the two moments the image set grows — and it is debris-tolerant in the same way — a crash between building an image and writing the submission row can orphan an image, so the sweep reclaims **by enumerating the daemon's actual overlay images, not by walking rows**, and tolerates an image with no matching submission exactly as Stage 4 tolerates a recording directory with no row.

The safety property that makes eviction simple: an overlay image is never irreplaceable. Step 6's submission-image helper already "refetches the pinned source when a rebuild is required," so evicting any overlay — even an active `ready` one — costs at most a rebuild on the next watch run, never data loss. Eviction is therefore always correct; the only thing to avoid is thrashing the images a viewer is about to watch. So the sweep **exempts the overlay images of the currently active `ready` submissions** (the watch-picker's live set, the image-world analogue of Stage 4's pinned recordings) and evicts the rest oldest-first. The exempt set comes from a storage read added in step 1 (`listActiveReadySubmissionIds`); everything not in it is a superseded or failed submission's image that the watch picker can never launch, so reclaiming it is pure win.

Two driver-interface additions make this expressible in driver-neutral terms, since the Stage 3 `ExecutionDriver` deliberately exposes only `ensureImage`/`launch` ([driver/index.ts](../../backend/src/driver/index.ts)): a way to **enumerate the overlay images the driver manages** (their opaque refs plus a creation timestamp, filtered to the overlay tag prefix so base images and unrelated images are never touched) and a best-effort **`removeImage(ref)`** that tolerates an already-absent image. Both are pure additions implemented in the Docker driver against `dockerode`; a Kubernetes driver implements the same two methods. Nothing above the driver learns Docker specifics.

Configuration joins `config.ts` alongside the recording-retention knobs it mirrors: `OVERLAY_IMAGE_BUDGET` (max retained overlay images, default to be confirmed against local Docker capacity — start at 50) and `OVERLAY_IMAGE_SWEEP_INTERVAL_MS` (default one hour, matching `RECORDING_SWEEP_INTERVAL_MS`). The sweep keeps the budget's worth of newest non-exempt images plus all exempt ones and removes the rest; if the exempt set alone exceeds the budget nothing non-exempt remains to evict, which is correct (those images are all live watch targets). Eviction runs through the driver, never around it, and reuses the deterministic tag scheme the build section above already defines (prefix, dependency-set version, submission id) so an image's submission id is recoverable from its tag.

## Pipeline and status

This step composes with steps 1-3 into the full validate-and-build pipeline: static check (step 3), build overlay, sandboxed load check, each a gate. A failure at any gate writes the submission row (step 1) to the matching rollup status with its reason: `static_failed`, `build_failed`, or `load_failed`, and the submission is **stored and shown to the owner rather than run** ([submission.md](../../docs/specs/submission.md), [execution.md](../../docs/specs/execution.md)). Only a submission that passes all three reaches `ready` and becomes runnable in step 6. Alongside the rollup, the worker (step 5) records the per-stage validation log: a `build` check and a `load` check, each `running` while it executes and then `passed`, or `failed` with the build error or the harness `validate` failure (`import_error`, `class_not_found`, `constructor_error`, `missing_hook`, including the captured Python error) as its `detail`. The structured failure line the harness emits is what becomes the `load` check's owner-visible detail, so the poller sees not just "load_failed" but the specific dynamic-load reason and error text. The orchestration lives in the backend's submission module and is invoked by the bounded validation worker introduced in step 5; this file owns the harness command, the driver image spec, and the load-check run.

## Tests

- **Harness unit/integration (Python):** `validate` against the worked example loads and reports success; against a manifest naming a non-existent class reports `class_not_found`; against a module that raises on import reports `import_error`; against a constructor that raises reports `constructor_error`; against a class missing `act` reports `missing_hook`. These exercise the command directly without the backend.
- **Backend build pipeline (Docker-gated):** a local-folder submission of the worked example builds an overlay on the base image and the load check passes; a fixture whose manifest names a missing class passes static validation but fails the load check with `load_failed`; a deliberately broken-import fixture yields `load_failed` or `build_failed` as appropriate. Caching default verified: a second build of the same unsuperseded submission reuses the overlay image when `DOCKER_IMAGE_POLICY=reuse`. Gated behind the Docker daemon like `backend-integration` and the Stage 4 e2e.
- **Overlay-image eviction:** the sweep's policy (budget, oldest-first, active-`ready` exemption, debris tolerance) is unit-tested against a **fake driver** whose `listOverlayImages`/`removeImage` are in-memory — no Docker needed for the policy itself, mirroring how the Stage 4 retention sweep tests over fakes. A test asserts a superseded submission's image is evicted while the active `ready` submission's image is kept, that an over-budget set is trimmed newest-kept, and that an enumerated image with no matching submission row is tolerated (reclaimed as debris, not crashed on). The real Docker `removeImage`/enumeration ride the Docker-gated suite.

## Done when

A repo whose manifest names a class that does not exist passes static validation but fails the sandboxed load check, recording `load_failed` with the Python error rather than producing a session, matching the exit criterion verbatim. The worked example and the extra Flappy Bird examples build an overlay and pass the load check, reaching `ready`. Builds run through the Stage 3 driver under the real sandbox profile, with caching as a driver-config default. The `ready` overlay image is what step 6's watch run launches. The eviction sweep reclaims superseded and failed submissions' overlay images on its budget while exempting the active `ready` images the watch picker can still launch, so overlay-image disk use stays bounded rather than growing one image per submission forever.
