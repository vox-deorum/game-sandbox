# Stage 6: Iterations and Leaderboards

Status: not started

## Goal

A full competition cycle works through an operator admin console: the operator declares and configures an iteration in the web UI, designs its match schedule, opens submissions, participants submit, the operator triggers the automated workflow and watches its container logs stream live, both boards appear on the environment page once the iteration's results are released, the operator opens the iteration for public play and feedback when it is ready, the operator can re-run the workflow and release/unrelease boards, and the previous iteration stays viewable as history when the next one starts.

> **Direction change from the spec.** Stage 6 replaces the configuration-file-plus-CLI model that [leaderboard.md](../docs/specs/leaderboard.md) originally described with an **operator admin UI** backed by an admin HTTP API, because the backend already holds the execution driver that launches the match containers, so it is the natural place to trigger runs and stream their logs. This is a deliberate spec revision, not a drift: [leaderboard.md](../docs/specs/leaderboard.md) and [frontend.md](../docs/specs/frontend.md) are updated in the same change set to describe the admin UI, iteration release status, the public play window, and re-runs. Per [the plan governance](README.md), the spec is the higher authority, so the spec moves first and the plan follows it.

## Scope

Implement per-iteration configuration per [leaderboard.md](../docs/specs/leaderboard.md), authored through the admin UI rather than a file: a **match design** declaring each match configuration's slot composition (which seats are built-in Naive baselines and which are submission seats, plus opponents for future multi-slot environments), the seeds, and a per-configuration **game count**; the template dependency-set version every submission in the iteration is built and run against (defaulting to the latest template release at declaration, see [submission.md](../docs/specs/submission.md)); and the optional overrides of per-step/per-episode time limits, messaging settings, and LLM budgets and allowlist. Each executable match configuration must assign at least one slot, and the workflow trigger rejects any design that resolves to an empty schedule. For the current Flappy Bird environment a match configuration is one submission in the single slot; the slot-composition fields become meaningful for environments with multiple slots. The per-step/per-episode timeout overrides take effect this stage; the messaging and LLM override fields are parsed and stored now so the format is stable, and take effect when the LLM gateway (Stage 9) and communication (Stage 8) land.

Implement **iteration lifecycle and release status** with three independent gates. An iteration carries a submission window (`open`/`closed`), a public play window (`open`/`closed`), and a release status (`unreleased`/`released`). Only one iteration per environment may be `open` for submissions at a time, and only one iteration per environment may be `open` for public play at a time. Existing Stage 5 seed iterations migrate as `unreleased`, submission-`open`, and play-`open` so local submissions and watch/play continue to work; new operator-declared iterations start `unreleased`, submission-`closed`, and play-`closed`. Opening either window is an explicit action; opening submissions fails if another iteration for that environment is already accepting submissions, and opening public play fails if another iteration for that environment is already the public play target. A user can see an iteration whenever any one of the three gates is in effect: submissions open, play open, or results released.

The gates answer different public questions. The open submission iteration is where the submit form writes, and it can be unreleased because opening submissions should not expose its boards. The play-open iteration is where normal watch/play sessions and rating writes attach, and it need not be released — the operator can let users watch and play an iteration before its results are released. The released status governs only whether the iteration's results (its boards and history) are shown to the public. These can be three different iterations: the operator can keep a released, play-open previous competition up for feedback while accepting submissions for the next round. An iteration's boards are operator-only until released, while an open submission window or an open play window still makes the iteration reachable for submitting, watching, and playing. Re-running the workflow recomputes boards in place; releasing results and opening play are explicit operator actions, so a re-run can be inspected before its boards are exposed. Declaring the next iteration leaves the previous released one reachable as history, with play closed whenever the operator wants it to be view-only.

Build the **operator admin console** and its **admin HTTP API** (the stable contract; the UI is the primary client but the routes are scriptable for headless deploys). Operator access is gated by an **operator allowlist** in deployment config, checked against the resolved identity from the Stage 4 seam (the mock user is an operator in local dev; the GitHub handle once OAuth lands). The admin surface lets the operator: declare and configure an iteration and its match design, open and close submissions, open and close public play, trigger the workflow, re-run it, release/unrelease results, and inspect status with a **live log stream** of the running match containers. There is no file-based CLI; the same admin routes are the automation surface.

Implement the **automated workflow**. A pure, deterministic **scheduler** expands an iteration's match design, slot composition plus game count, over a trigger-time snapshot of the iteration's active `ready` submissions and the built-in Naive baseline into a concrete, balanced run schedule. In Stage 6, executable match configurations support zero or one submission seat; multi-submission-seat execution is stored as a future-capable config shape but rejected until Stage 7 defines Hearts balancing. `games` means total games per resolved assignment, with seeds round-robined by run index. The workflow trigger snapshots the iteration config, dependency version, eligible ready submissions, and resolved schedule before enqueueing the background runner; later resubmissions or status changes cannot alter that run. The runner executes the persisted schedule sequentially on the same host so timings are comparable, one container per match through the Stage 3 execution driver using the Stage 5 submission images, seeds passed to both the environment and the agents, per-step and per-episode timeouts from the environment defaults or the iteration overrides, every run recorded, and container logs captured for the admin WebSocket stream. Wall-clock agent compute time is aggregated from the recordings the Stage 2 harness already produces: final `score` for episode score and the weighted per-decision mean of `decision_ms + learn_ms` now, with future hook and LLM timing added later. In this single-agent stage an attributable failing or timed-out agent keeps its final recorded score and a failure flag; infrastructure failures do not invent agent result rows. The Naive baseline is always scheduled, so the board always has a baseline row when the schedule is runnable. Re-running is idempotent: a fresh completed run replaces the prior run's board and placements for that iteration.

Compute the **automated board** from the latest completed run: agents ranked by mean episode score, where the environment's leaderboard score is normalized so higher is better, with mean wall-clock agent compute time as a separate column, never folded into one number. Persist per-agent **automated placements** so the agent profile can show them. Leaderboard recordings from the current completed run are retained for as long as their iteration stays viewable, per [recording.md](../docs/specs/recording.md), while superseded-run recordings become eligible for the extended Stage 4 retention sweep.

Implement **ratings** per [frontend.md](../docs/specs/frontend.md): after any rateable session, watch or play, the user rates each involved rateable agent 1 to 5, including the Naive baseline when it was involved; one effective rating per user per agent per iteration, overwritten on re-rating while the play window is open; ratings of the user's own submitted agent excluded. Sessions gain explicit iteration attribution from the play-open target, the selected submitted agent's iteration, or an operator-selected iteration, never by guessing from the open submission iteration. The rating is guided by up to two optional **rating prompts** shown at rating time: one the operator sets on the iteration (applies to every agent), and one an agent's author sets for their submission (applies only to that agent). The prompts are context for the single 1-to-5 rating, not extra scores. The **human-feedback board** shows mean rating and count, ranking only agents with at least three ratings and showing under-threshold rows unranked.

Surface it all on the frontend: a per-environment, per-iteration **Leaderboards** view with both boards side by side for the current released iteration, links to historical iterations, leaderboard placements on agent profiles, replays linked from board rows, and the operator admin console for everything above.

## Build order

Each step is its own subplan under [stage-06/](stage-06/), plus a cross-cutting [testing, CI, and docs](stage-06/8-testing-ci-and-docs.md) companion. Docker-free, demonstrable slices come first.

1. **[Iteration config, release status, and storage](stage-06/1-iteration-config-and-storage.md).** Extend the Stage 5 `iterations` record into full configuration (match design, overrides, deps_version default, `submission_status`, `play_status`, `release_status`, ordering); add session iteration attribution, run/game/result/placement/rating storage, trigger-time roster and schedule snapshots, leaderboard-recording retention protection, the migration, the storage methods, and the operator-allowlist `isOperator` seam. Docker-free. The data foundation everything attaches to.
2. **[Matchmaking and schedule generation](stage-06/2-matchmaking-schedule.md).** A pure, deterministic function that expands a match design (slot composition + game count) over the active `ready` submissions plus the Naive baseline and seeds into a balanced concrete schedule. Fully unit-testable, Docker-free. First demonstrable slice.
3. **[Admin HTTP API and operator gating](stage-06/3-admin-api-and-gating.md).** The operator-gated admin routes: declare/configure, open/close submissions, open/close public play, release/unrelease results, trigger/re-run the workflow, inspect status, and stream run logs. The stable contract the admin UI and any headless client use.
4. **[Automated workflow runner](stage-06/4-automated-workflow-runner.md).** Sequential single-host execution of the snapshotted schedule, one container per match through the Stage 3 driver on Stage 5 images, seeds, timeouts, per-run recording, container-log capture for the admin WebSocket stream, total agent compute aggregation from recordings, the attributable-failure rule, and idempotent re-run. Docker-gated.
5. **[Automated board and retention](stage-06/5-automated-board-and-retention.md).** Compute the board (normalized mean score ranking, separate mean-agent-compute column), persist automated placements, link best-score replays per row, and extend the Stage 4 retention sweep to keep current-run leaderboard recordings for as long as the iteration is viewable.
6. **[Ratings and the human-feedback board](stage-06/6-ratings-and-human-board.md).** The rating write/read API with the one-effective-per-user-per-agent-per-iteration and own-submitted-agent-excluded rules, Naive ratings, the operator iteration rating prompt and the author per-submission rating prompt surfaced at rating time, the post-session rating UI on the watch and play flows, and the human board (mean + count, ranked at three ratings, under-threshold rows unranked).
7. **[Frontend: leaderboards and admin console](stage-06/7-frontend-leaderboards-and-admin.md).** The public Leaderboards view (both boards side by side on the environment page, historical links, profile placements, board-row replay links, separate submit and play targets) and the operator admin console driving the step-3 API with a live log stream. The console's lifecycle controls reflect the three independent gates (submissions, play, release).

## Done when

The operator declares a submission-closed, play-closed, unreleased iteration in the admin console, designs a Flappy Bird match configuration of one submission seat with two seeds and a game count, opens submissions after any previous open submission iteration is closed, two test submissions land, and triggers the workflow; the trigger snapshots the eligible submissions and concrete schedule, the console streams the match container logs over WebSocket, the workflow produces a board where every run has a replay and the Naive baseline is ranked alongside the submissions, and re-running with the same configuration reproduces the scores of deterministic agents. The iteration's boards are operator-only until the operator releases them, after which they appear on the environment page; public watch/play controls remain disabled until the operator opens the play window. Re-running and re-releasing updates boards while the previous released iteration stays reachable as history. Ratings from three test users rank an agent on the human board only after the third rating arrives, rating writes are accepted only for sessions attached to a play-open iteration, the rating UI shows the operator's iteration prompt and the agent author's per-submission prompt when set, ratings of a user's own submitted agent are excluded, the Naive baseline can be rated, and declaring the next iteration can open submissions for the new round while the old released boards stay reachable.
