# Stage 6: Iterations and Leaderboards

Status: not started

## Goal

A full competition cycle works through an operator admin console: the operator declares and configures an iteration in the web UI, designs its match schedule, opens submissions, participants submit, the operator triggers the automated workflow and watches its container logs stream live, both boards appear on the environment page once the iteration is published, the operator can re-run the workflow and publish/unpublish boards, and the previous iteration stays viewable as history when the next one starts.

> **Direction change from the spec.** Stage 6 replaces the configuration-file-plus-CLI model that [leaderboard.md](../docs/specs/leaderboard.md) originally described with an **operator admin UI** backed by an admin HTTP API, because the backend already holds the execution driver that launches the match containers, so it is the natural place to trigger runs and stream their logs. This is a deliberate spec revision, not a drift: [leaderboard.md](../docs/specs/leaderboard.md) and [frontend.md](../docs/specs/frontend.md) are updated in the same change set to describe the admin UI, iteration visibility, and re-runs. Per [the plan governance](README.md), the spec is the higher authority, so the spec moves first and the plan follows it.

## Scope

Implement per-iteration configuration per [leaderboard.md](../docs/specs/leaderboard.md), authored through the admin UI rather than a file: a **match design** declaring each match configuration's slot composition (which seats are built-in Naive baselines and which are submission seats, plus opponents for future multi-slot environments), the seeds, and a per-configuration **game count**; the template dependency-set version every submission in the iteration is built and run against (defaulting to the latest template release at declaration, see [submission.md](../docs/specs/submission.md)); and the optional overrides of per-step/per-episode time limits, messaging settings, and LLM budgets and allowlist. For the current Flappy Bird environment a match configuration is one submission in the single slot; the slot-composition fields become meaningful for environments with multiple slots. The per-step/per-episode timeout overrides take effect this stage; the messaging and LLM override fields are parsed and stored now so the format is stable, and take effect when the LLM gateway (Stage 9) and communication (Stage 8) land.

Implement **iteration lifecycle and visibility**. An iteration carries a submission window (`open`/`closed`) and a visibility (`draft`/`published`). A `draft` iteration and its boards are visible only to operators: the operator declares it, opens submissions, triggers and inspects the workflow, verifies the boards privately, and then **publishes** it so it appears on the environment page and in history. Re-running the workflow recomputes the boards in place; publishing is an explicit operator action, so a re-run can be inspected before it is exposed. Declaring the next iteration leaves the previous published one reachable as history.

Build the **operator admin console** and its **admin HTTP API** (the stable contract; the UI is the primary client but the routes are scriptable for headless deploys). Operator access is gated by an **operator allowlist** in deployment config, checked against the resolved identity from the Stage 4 seam (the mock user is an operator in local dev; the GitHub handle once OAuth lands). The admin surface lets the operator: declare and configure an iteration and its match design, open and close submissions, trigger the workflow, re-run it, publish/unpublish, and inspect status with a **live log stream** of the running match containers. There is no file-based CLI; the same admin routes are the automation surface.

Implement the **automated workflow**. A pure, deterministic **scheduler** expands an iteration's match design — slot composition plus game count — over the iteration's active `ready` submissions and the built-in Naive baseline into a concrete, balanced run schedule (every ready submission rotated through the submission seat, the other seats filled per the composition, multiplied across seeds). The runner executes that schedule sequentially on the same host so timings are comparable, one container per match through the Stage 3 execution driver using the Stage 5 submission images, seeds passed to both the environment and the agents, per-step and per-episode timeouts from the environment defaults or the iteration overrides, every run recorded, and container logs captured for the admin stream. Wall-clock time per decision and per episode is aggregated from the recordings the Stage 2 harness already produces (per-step `score` and per-agent `decision_ms`). In this single-agent stage a failing or timed-out agent is recorded as that agent's result; the same rule applies per slot once multi-agent match configurations arrive (Stage 7), without aborting the whole iteration. The Naive baseline is always scheduled, so the board always has a baseline row. Re-running is idempotent: a fresh run replaces the prior run's results and recordings for that iteration.

Compute and store the **automated board**: agents ranked by mean episode score, where the environment's leaderboard score is normalized so higher is better, with mean wall-clock time per decision as a separate column, never folded into one number. Persist per-agent **placements** so the agent profile can show them. Leaderboard recordings are retained for as long as their iteration stays viewable, per [recording.md](../docs/specs/recording.md), extending the Stage 4 retention sweep.

Implement **ratings** per [frontend.md](../docs/specs/frontend.md): after any session, watch or play, the user rates each involved agent 1 to 5; one effective rating per user per agent per iteration, overwritten on re-rating; ratings of the user's own agent excluded. The **human-feedback board** shows mean rating and count, ranking only agents with at least three ratings.

Surface it all on the frontend: a per-environment, per-iteration **Leaderboards** view with both boards side by side for the current published iteration, links to historical iterations, leaderboard placements on agent profiles, replays linked from board rows, and the operator admin console for everything above.

## Build order

Each step is its own subplan under [stage-06/](stage-06/), plus a cross-cutting [testing, CI, and docs](stage-06/8-testing-ci-and-docs.md) companion. Docker-free, demonstrable slices come first.

1. **[Iteration config, visibility, and storage](stage-06/1-iteration-config-and-storage.md).** Extend the Stage 5 `iterations` record into full configuration (match design, overrides, deps_version default, `submission_status`, `visibility`, ordering); add the `iteration_runs`, automated-board, and `ratings` tables; the migration; the storage methods; and the operator-allowlist `isOperator` seam. Docker-free. The data foundation everything attaches to.
2. **[Matchmaking and schedule generation](stage-06/2-matchmaking-schedule.md).** A pure, deterministic function that expands a match design (slot composition + game count) over the active `ready` submissions plus the Naive baseline and seeds into a balanced concrete schedule. Fully unit-testable, Docker-free. First demonstrable slice.
3. **[Admin HTTP API and operator gating](stage-06/3-admin-api-and-gating.md).** The operator-gated admin routes: declare/configure, open/close submissions, publish/unpublish, trigger/re-run the workflow, inspect status, and stream run logs. The stable contract the admin UI and any headless client use.
4. **[Automated workflow runner](stage-06/4-automated-workflow-runner.md).** Sequential single-host execution of the schedule, one container per match through the Stage 3 driver on Stage 5 images, seeds, timeouts, per-run recording, container-log capture for the admin stream, timing aggregation from recordings, the failing-agent rule, and idempotent re-run. Docker-gated.
5. **[Automated board and retention](stage-06/5-automated-board-and-retention.md).** Compute and store the board (normalized mean score ranking, separate mean-decision-time column), persist placements, link replays per row, and extend the Stage 4 retention sweep to keep leaderboard recordings for as long as the iteration is viewable.
6. **[Ratings and the human-feedback board](stage-06/6-ratings-and-human-board.md).** The rating write/read API with the one-effective-per-user-per-agent-per-iteration and own-agent-excluded rules, the post-session rating UI on the watch and play flows, and the human board (mean + count, ranked at three ratings).
7. **[Frontend: leaderboards and admin console](stage-06/7-frontend-leaderboards-and-admin.md).** The public Leaderboards view (both boards side by side on the environment page, historical links, profile placements, board-row replay links) and the operator admin console driving the step-3 API with a live log stream.

## Done when

The operator declares an iteration in the admin console, designs a Flappy Bird match configuration of one submission seat with two seeds and a game count, opens submissions, two test submissions land, and triggers the workflow; the console streams the match container logs, the workflow produces a board where every run has a replay and the Naive baseline is ranked alongside the submissions, and re-running with the same configuration reproduces the scores of deterministic agents. The iteration's boards are operator-only until the operator publishes, after which they appear on the environment page; re-running and re-publishing updates them while the previous published iteration stays reachable as history. Ratings from three test users rank an agent on the human board only after the third rating arrives, ratings of a user's own agent are excluded, and declaring the next iteration resets both boards for the current view while the old published ones stay reachable. </content> </invoke>
