# Stage 6: Seasons and Leaderboards

Status: not started

## Goal

A full competition cycle runs through an operator admin console. The operator declares and configures a season in the web UI, designs its match schedule, and opens submissions. Participants submit. The operator triggers the automated workflow and watches its container logs stream live. Once the season's results are released, both boards appear on the environment page. The operator opens the season for public play and feedback when it is ready, and can re-run the workflow and release or unrelease boards. When the next season starts, the previous one stays viewable as history.

> **Direction change from the spec.** Stage 6 replaces the configuration-file-plus-CLI model that [leaderboard.md](../docs/specs/leaderboard.md) originally described with an **operator admin UI** backed by an admin HTTP API. The backend already holds the execution driver that launches the match containers, so it is where runs get triggered and logs get streamed. This is a spec revision, not a drift: [leaderboard.md](../docs/specs/leaderboard.md) and [frontend.md](../docs/specs/frontend.md) are updated in the same change set to describe the admin UI, season release status, the public play window, and re-runs. Per [the plan governance](README.md), the spec is the higher authority, so the spec moves first and the plan follows it.

## Scope

Implement per-season configuration per [leaderboard.md](../docs/specs/leaderboard.md), authored through the admin UI rather than a file. It has three parts. First, a **match design** that declares each match configuration's slot composition (which seats are built-in Naive baselines and which are submission seats, plus opponents for future multi-slot environments), the seeds, and a per-configuration **game count**. Second, the template dependency-set version every submission in the season is built and run against; it defaults to the latest template release at declaration (see [submission.md](../docs/specs/submission.md)). Third, the optional overrides of per-step/per-episode time limits, messaging settings, and LLM budgets and allowlist. Each executable match configuration must assign at least one slot, and the workflow trigger rejects any design that resolves to an empty schedule. For the current Flappy Bird environment, a match configuration is one submission in the single slot; the slot-composition fields become meaningful for environments with multiple slots. The per-step/per-episode timeout overrides take effect this stage. The messaging and LLM override fields are parsed and stored now so the format is stable, and they take effect when the LLM gateway (Stage 9) and communication (Stage 8) land.

Implement **season lifecycle and release status** with three independent gates. A season carries a submission window (`open`/`closed`), a public play window (`open`/`closed`), and a release status (`unreleased`/`released`). Per environment, only one season may be `open` for submissions at a time, and only one may be `open` for public play at a time. Existing Stage 5 seed seasons migrate as `unreleased`, submission-`open`, and play-`open` so local submissions and watch/play keep working. New operator-declared seasons start `unreleased`, submission-`closed`, and play-`closed`. Opening either window is an explicit action. Opening submissions fails if another season for that environment is already accepting submissions, and opening public play fails if another season for that environment is already the public play target. A user can see a season whenever any one of the three gates is in effect: submissions open, play open, or results released.

The gates answer different public questions. The open submission season is where the submit form writes. It can be unreleased, because opening submissions should not expose its boards. The play-open season is where normal watch/play sessions and rating writes attach. It need not be released: the operator can let users watch and play a season before its results go public. The released status governs only whether the season's results (its boards and history) are shown to the public. These can be three different seasons. For example, the operator can keep a released, play-open previous competition up for feedback while accepting submissions for the next round. A season's boards are operator-only until released, but an open submission window or open play window still makes the season reachable for submitting, watching, and playing. Re-running the workflow recomputes boards in place. Releasing results and opening play are explicit operator actions, so a re-run can be inspected before its boards are exposed. Declaring the next season leaves the previous released one reachable as history, with play closed whenever the operator wants it to be view-only.

Build the **operator admin console** and its **admin HTTP API**. The API is the stable contract: the UI is the primary client, but the routes are scriptable for headless deploys. Operator access is gated by an **operator allowlist** in deployment config, checked against the resolved identity from the Stage 4 seam (the mock user is an operator in local dev; the GitHub handle once OAuth lands). The admin surface lets the operator declare and configure a season and its match design, open and close submissions, open and close public play, trigger the workflow, re-run it, release or unrelease results, and inspect status with a **live log stream** of the running match containers. There is no file-based CLI; the same admin routes are the automation surface.

Implement the **automated workflow**. A pure, deterministic **scheduler** expands a season's match design (slot composition plus game count) into a concrete, balanced run schedule. It works from a trigger-time snapshot of the season's active `ready` submissions and the built-in Naive baseline. In Stage 6, executable match configurations support zero or one submission seat; multi-submission-seat execution is stored as a future-capable config shape but rejected until Stage 7 defines Hearts balancing. `games` means total games per resolved assignment, with seeds round-robined by run index. The workflow trigger snapshots the season config (which includes the dependency version), eligible ready submissions, and resolved schedule before enqueueing the background runner; later resubmissions or status changes cannot alter that run. The runner executes the persisted schedule sequentially on the same host so timings are comparable. It runs one container per match through the Stage 3 execution driver, using the Stage 5 submission images. Seeds are passed to both the environment and the agents. Per-step and per-episode timeouts come from the environment defaults or the season overrides. Every run is recorded, and container logs are captured for the admin WebSocket stream. Wall-clock agent compute time is aggregated from the recordings the Stage 2 harness already produces: final `score` for episode score, and the weighted per-decision mean of `decision_ms + learn_ms` for now, with hook and LLM timing added later. In this single-agent stage, an attributable failing or timed-out agent keeps its final recorded score and a failure flag; infrastructure failures do not invent agent result rows. The Naive baseline is always scheduled, so the board always has a baseline row when the schedule is runnable. Re-running is idempotent: a fresh completed run replaces the prior run's board and placements for that season.

Compute the **automated board** from the latest completed run. Agents are ranked by mean episode score, with the environment's leaderboard score normalized so higher is better. Mean wall-clock agent compute time is a separate column, never folded into the ranking number. Persist per-agent **automated placements** so the agent profile can show them. Leaderboard recordings from the current completed run are retained for as long as their season stays viewable, per [recording.md](../docs/specs/recording.md). Superseded-run recordings become eligible for the extended Stage 4 retention sweep.

Implement **ratings** per [frontend.md](../docs/specs/frontend.md). After any rateable session, whether watch or play, the user rates each involved rateable agent 1 to 5, including the Naive baseline when it was involved. There is one effective rating per user per agent per season, overwritten on re-rating while the play window is open. Ratings of the user's own submitted agent are excluded. Sessions get explicit season attribution from the play-open target, the selected submitted agent's season, or an operator-selected season, never by guessing from the open submission season. The rating is guided by up to two optional **rating prompts** shown at rating time: one the operator sets on the season (applies to every agent), and one an agent's author sets for their submission (applies only to that agent). The prompts are context for the single 1-to-5 rating, not extra scores. The **human-feedback board** shows mean rating and count. It ranks only agents with at least three ratings and shows under-threshold rows unranked.

Surface it all on the frontend with a per-environment, per-season **Leaderboards** view. It shows both boards side by side for the current released season, links to historical seasons, leaderboard placements on agent profiles, replays linked from board rows, and the operator admin console for everything above.

## Build order

Each step is its own subplan under [stage-06/](stage-06/), plus a cross-cutting [testing, CI, and docs](stage-06/8-testing-ci-and-docs.md) companion. Docker-free, demonstrable slices come first.

1. **[Season config, release status, and storage](stage-06/1-season-config-and-storage.md).** Extend the Stage 5 `seasons` record into full configuration (match design, overrides, deps_version default, `submission_status`, `play_status`, `release_status`, ordering). Add session season attribution, run/game/result/placement/rating storage, trigger-time roster and schedule snapshots, leaderboard-recording retention protection, the fresh-build schema declarations, the storage methods, and the operator-allowlist `isOperator` seam. Docker-free. The data foundation everything attaches to.
2. **[Matchmaking and schedule generation](stage-06/2-matchmaking-schedule.md).** A pure, deterministic function that expands a match design (slot composition + game count) into a balanced concrete schedule, working from the active `ready` submissions, the Naive baseline, and the seeds. Fully unit-testable, Docker-free. First demonstrable slice.
3. **[Admin HTTP API and operator gating](stage-06/3-admin-api-and-gating.md).** The operator-gated admin routes: declare/configure, open/close submissions, open/close public play, release/unrelease results, trigger/re-run the workflow, inspect status, and stream run logs. The stable contract the admin UI and any headless client use.
4. **[Automated workflow runner](stage-06/4-automated-workflow-runner.md).** Sequential single-host execution of the snapshotted schedule: one container per match through the Stage 3 driver on Stage 5 images, seeds, timeouts, per-run recording, container-log capture for the admin WebSocket stream, total agent compute aggregation from recordings, the attributable-failure rule, and idempotent re-run. Docker-gated.
5. **[Automated board and retention](stage-06/5-automated-board-and-retention.md).** Compute the board (normalized mean score ranking, separate mean-agent-compute column), persist automated placements, link best-score replays per row, and extend the Stage 4 retention sweep to keep current-run leaderboard recordings for as long as the season is viewable.
6. **[Ratings and the human-feedback board](stage-06/6-ratings-and-human-board.md).** The rating write/read API with the one-effective-per-user-per-agent-per-season and own-submitted-agent-excluded rules, Naive ratings, the operator season rating prompt and the author per-submission rating prompt surfaced at rating time, the post-session rating UI on the watch and play flows, and the human board (mean + count, ranked at three ratings, under-threshold rows unranked).
7. **[Frontend: leaderboards and admin console](stage-06/7-frontend-leaderboards-and-admin.md).** The public Leaderboards view (both boards side by side on the environment page, historical links, profile placements, board-row replay links, separate submit and play targets) and the operator admin console driving the step-3 API with a live log stream. The console's lifecycle controls reflect the three independent gates (submissions, play, release).

## Done when

The operator declares a submission-closed, play-closed, unreleased season in the admin console and designs a Flappy Bird match configuration of one submission seat with two seeds and a game count. After any previous open submission season is closed, the operator opens submissions, two test submissions land, and the operator triggers the workflow. The trigger snapshots the eligible submissions and concrete schedule. The console streams the match container logs over WebSocket. The workflow produces a board where every run has a replay and the Naive baseline is ranked alongside the submissions. Re-running with the same configuration reproduces the scores of deterministic agents. The season's boards are operator-only until the operator releases them, after which they appear on the environment page; public watch/play controls remain disabled until the operator opens the play window. Re-running and re-releasing updates boards while the previous released season stays reachable as history. Ratings from three test users rank an agent on the human board only after the third rating arrives. Rating writes are accepted only for sessions attached to a play-open season. The rating UI shows the operator's season prompt and the agent author's per-submission prompt when set. Ratings of a user's own submitted agent are excluded, and the Naive baseline can be rated. Declaring the next season can open submissions for the new round while the old released boards stay reachable.
