Part of [Stage 6](../stage-06-leaderboards.md). This is build-order step 6. It covers four things: collecting 1-5 ratings after a session; enforcing the one-effective-rating and own-agent-exclusion rules; showing the two optional rating prompts that guide the rater (the operator's season prompt and the agent author's per-submission prompt); and computing the human-feedback board (mean rating, population standard deviation, and count, ranked only at three ratings). The work spans backend and frontend. The backend covers the `ratings` and `agent_rating_prompts` tables, the `seasons.rating_prompt` column from step 1, and the write/read API. The frontend covers the post-session rating UI on the watch and play flows, plus the author's prompt editor on the agent profile.

## Rating rules

Per [frontend.md](../../docs/specs/frontend.md):

- After a rateable session (watch or play), the user can rate each involved rateable agent on a 1-5 scale.
- **One effective rating per user per agent per season**: re-rating overwrites the previous value, keyed by the shared `AgentRef` columns from step 1.
- **Own-agent ratings are excluded**: a user cannot rate their own submitted agent; the API rejects it and the UI does not offer it for the user's own agent.
- The built-in Naive baseline has no owner and is rateable when it appears alongside a submitted agent. A pure Naive-only watch recording has no rating panel.
- Ratings feed only the **human-feedback** board and never the automated one.

Ratings target the exact `AgentRef` values involved in the session, not only submissions. A session is tied to a season through the nullable `sessions.season_id` added in step 1. For new watch and play sessions, this is written from the selected public play season or the selected submitted agent's season. It is never resolved from the open submission season, because submissions and play can be open on different rounds.

The authoritative source of which agents were involved is the **finished recording's header `players` attribution** ([recording.md](../../docs/specs/recording.md)). The header names every slot's driver, submission, Naive baseline, or human, for both submitted and built-in slots. End-of-session feedback runs after the recording is finalized, so the header is available at rating time. The route reads it to build the allowed rateable-agent set and falls back to `session_submissions` when a header read fails. That fallback recovers submitted agents but not built-in slots, which is sufficient for a pure Naive-only recording because that case intentionally has no feedback panel.

The header `players` entry shape is the recording schema's, not `AgentRef`. Each entry has `kind: 'human' | 'agent'` with optional `submission_id` and `user`. Map them deterministically. An `agent` entry with a `submission_id` becomes `{ kind: 'submission', submission_id }`. An `agent` entry with no `submission_id` becomes `{ kind: 'builtin-naive' }`, keyed on the absence of `submission_id` and **not** on the `"Naive agent"` label string, which is display-only. Skip `human` entries, since humans are not rateable agents. After deduplication, return an empty rateable set if every remaining entry is `builtin-naive`. This is the one place header attribution is translated into the `AgentRef` that the rest of the stage stores.

Three kinds of session cannot receive new or updated public ratings: sessions with null `season_id` (no competition boundary), sessions without a finalized recording, and sessions attached to a season whose play window is closed.

## Rating prompts

Two optional prompts guide what the human is rating; both are guidance for the single 1-to-5 score, not extra scores (see [leaderboard.md](../../docs/specs/leaderboard.md) and [frontend.md](../../docs/specs/frontend.md)):

- The **season prompt** is the operator's `seasons.rating_prompt` (step 1), applying to every agent in the season.
- The **author prompt** is the agent owner's `agent_rating_prompts` row for `(season_id, owner_user_id)` (step 1). It applies only to that owner's agent. The author sets and edits it from their agent profile. It is presentation metadata, not part of the pinned submission.

The Naive baseline has no author, so only the season prompt applies to it. For each rateable agent, the rating-read endpoint returns the season prompt and that agent's author prompt (resolved by the involved submission's `user_id`). This lets the UI show both next to the rating control.

## API

New routes in the backend HTTP layer, attributing each rating to the resolved identity from the Stage 4 seam (never a body-supplied user):

- **Rate**: `POST /api/sessions/:sessionId/ratings`. The caller must be on the public-session allowlist; otherwise the route returns `403 not_allowlisted`. The body is a list of `{ agent, score }`, where `agent` is the wire form of `AgentRef` (`{ kind: 'submission', submission_id }` or `{ kind: 'builtin-naive' }`). The wire form carries no `user_id`. The route resolves `sessions.season_id` and runs a series of checks. It rejects null-season sessions with `409 session_not_rateable`, sessions without a finalized recording with `409 session_not_finished`, and sessions whose season is not play-open with `409 play_closed`. It resolves the allowed agent refs actually involved in that session (from the recording header above), rejects a score outside 1-5, and rejects rating an agent not actually in that session. For each submitted agent, it resolves the owner `user_id` **server-side** from the submission and rejects rating the caller's own submitted agent (resolved `user_id == identity`) with a specific reason. The client never asserts the owner. The route validates the whole payload before writing any rating, so a mixed valid/invalid request does not partially save. Each accepted rating is an `upsertRating` (step 1), so submitting again overwrites while play remains open. The route returns the caller's current effective ratings for the session's agents, so the UI can reflect the saved state.
- **Read own ratings and prompts**: `GET /api/sessions/:sessionId/ratings`. For each rateable agent in the session, this returns the caller's existing rating, a viewer-appropriate `display_name`, and the two applicable prompts: the season's `rating_prompt` and that agent's author prompt. While play is open, regular users receive numbered submitted-agent labels and `Your agent`; operators retain identified labels. Once play closes, the stored owner-based labels return and the response is read-only. The existing rating lets the post-session UI pre-fill what the user already rated, and returning the prompts avoids a second request.
- **Set author prompt**: `PUT /api/seasons/:seasonId/agent-rating-prompt`. The agent owner sets or clears their own per-season author prompt with `upsertAgentRatingPrompt`, keyed by the caller's resolved identity, never a body-supplied user. The caller must have an agent (a submission) in that season; otherwise the route returns `409 no_agent_in_season`. This is a participant action, not an operator one, so it is **not** under `/api/admin`. The owner reads it back with `GET /api/seasons/:seasonId/agent-rating-prompt` to populate the editor on their agent profile.
- **Human board read**: folded into the public board service (step 5/7). `getHumanBoard(seasonId)` aggregates `ratings` by `AgentRef` into mean, population standard deviation, and count, **ranking only agents with at least three ratings**. Agents with one or two ratings appear unranked below the ranked set, with all three statistics, so feedback can be seen accumulating without assigning a rank. Public reads serve only a released season's human board; the admin view can also see an unreleased season's.

## Frontend: post-session rating UI

At the end of a session, immediately above the canvas, present a rating control per involved agent. The panel is absent while the session runs and enters after termination with a short expanding downward reveal using the shared motion tokens:

- A 1-5 control (stars or segmented buttons) per rateable agent in the session, built on the Stage 4.5 primitives so it inherits the design system. The user's **own** submitted agent is shown without a rating control, labeled as the user's agent, reflecting the exclusion. The Naive baseline gets a normal rating control in a mixed session with a submitted agent. A pure Naive-only recording renders no panel.
- **The two prompts are shown with the control** when present. The season instructions appear once above the list, and agent instructions appear only beside the applicable agent. Both come from the rating-read payload, so no extra request is needed. The Naive baseline has no agent instructions.
- During a playable season, non-operators see blind submitted-agent labels in the panel, live attribution, and replay attribution. Operators retain identities. Closing play restores the canonical owner-based labels without changing the recording.
- Submitting calls the rate route. The control then shows the saved state and allows changing it, which overwrites. The UI reads the caller's existing ratings, so reopening a session the user already rated shows their prior values.
- This attaches to the end-of-session points of **both** the watch flow (Stage 5 watch-run) and the play flow (Stage 4 live play), since ratings come from any session. The control is the same component in both; only the set of involved agents differs. Watch is single-agent for now, and the multi-agent case in Stage 7 reuses the same component for every seat.

## Frontend: author prompt editor

> **Superseded by a later change.** The standalone `AuthorPromptEditor.vue` described in this section was removed. Authors now set the rating prompt directly in the **Submit an Agent** form (`SubmitAgentForm.vue`), saved against the submission-open season once the agent is accepted and editable only while that window stays open (it locks when submissions close, even if play is still open). The backend enforces that lifecycle on `PUT /api/seasons/:seasonId/agent-rating-prompt`. See [frontend.md](../../docs/specs/frontend.md). The text below records the original stage-6 design.

On the agent profile ([frontend.md](../../docs/specs/frontend.md), Stage 5.6), the agent's **owner** gets a small editor to set or clear their per-submission rating prompt, "what should people evaluate about my agent?" It is shown only to the owner. When submission and play windows point at different seasons, it targets the owner's active submission in the play-open season; when no such submission exists, it falls back to the active submission in the submission-open season. The prompt is plain presentation metadata, kept distinct from the submission's validated artifact and build/validation status on the same page. Non-owners do not see the editor. They only see the prompt later at rating time, if they rate this agent.

The human-feedback board's display (mean + population standard deviation + count, with the three-rating ranking rule) lives in the Leaderboards view built in step 7. This step provides its data (`getHumanBoard`) and the collection UI.

## Tests

- **Backend (Vitest, `:memory:`):** a rating of a submitted agent in a session is stored under the caller's identity. A Naive rating in a mixed session is stored and aggregates under `builtin-naive`, while a pure Naive-only recording returns no rateable agents. A non-allowlisted rating write is rejected. A second rating by the same user for the same agent ref overwrites rather than duplicating while play is open. A score outside 1-5 is rejected. Rating an agent not in the session is rejected. A mixed valid/invalid payload writes nothing. The own-agent rejection resolves the owner server-side, so a body that omits or spoofs the owner still cannot rate the caller's own agent. A session with null `season_id` returns `session_not_rateable`. A session without a finalized recording returns `session_not_finished`. A closed play window returns `play_closed` for writes and read-only data for reads. Reading own ratings returns the effective values **and the applicable season and author prompts per agent**. Submitted-agent watch listings and launches use the play-open season when submission and play targets differ. The set-author-prompt route stores under the caller's identity and returns `409 no_agent_in_season` for a caller with no submission in the season. `getHumanBoard` returns mean, population standard deviation, and count per agent ref, ranks only agents with at least three ratings, and surfaces under-threshold agents as unranked. An unreleased season's human board is admin-only.
- **Frontend (Vitest, jsdom, mocked fetch):** the post-session UI renders a rating control per involved rateable agent, including Naive and none for the user's own submitted agent. The season and author prompts render next to the right agents, and Naive shows only the season prompt. Submitting posts the scores and reflects the saved state. Reopening pre-fills prior ratings. Changing a rating re-posts and overwrites. The agent-profile author-prompt editor shows only to the owner, posts the prompt, and reflects the saved value. Follows the Stage 4/5 frontend-unit pattern (no canvas, no real network).
