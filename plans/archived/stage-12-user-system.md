# Stage 12: User system

Status: complete. Steps 1 through 6 provide Better Auth cookie sessions on the shared SQLite database, the identity seam and status authorization, the frontend sign-in and session, the admin Users page, GitHub account linking and public profile identity, and the testing/CI/docs closeout. The `SESSION_ALLOWLIST`, `OPERATOR_ALLOWLIST`, `VITE_SANDBOX_USER`, `x-sandbox-user`, and `not_allowlisted` names appear nowhere in code, tests, docs, or CI.

## Goal

Identity becomes real. The mock auto-logon that Stage 4 left as a seam, the `x-sandbox-user` header with its `dev-user` fallback and its two environment-variable allowlists, is replaced by [Better Auth](https://www.better-auth.com/): cookie-backed sessions, GitHub OAuth sign-in, an email and password sign-in for accounts the deployment creates, and a built-in admin seeded from deployment configuration. Every user carries a role-derived status — `pending`, `normal`, or `admin` — that is the authorization source for what an authenticated user may do, while `banned` is a standalone flag Better Auth enforces by revoking sessions and blocking sign-in. The `SESSION_ALLOWLIST` and `OPERATOR_ALLOWLIST` variables are removed. An admin manages the roster, searching, creating, approving, banning, and promoting users, from a Users page in the web app.

The stub was always meant to be temporary. Stage 3 resolves the acting user in one function so that real authentication could replace it without touching callers, and Stage 6 built its operator gate over the same seam. This stage collects on that design: it swaps the one resolution point for a session lookup, folds the two allowlists into the status model, and gives the deployment the account and roster controls a real class needs.

## Scope

Authentication with Better Auth. The backend embeds the Better Auth server on the same SQLite database the storage layer already owns, mounted as a catch-all `/api/auth/*` route on the existing Fastify app. Two sign-in methods exist: GitHub OAuth, which is optional and whose button is hidden when the deployment configures no OAuth app, and email with password, with self-registration disabled. Accounts come into existence only three ways: the seeded admin, admin-created users, and GitHub sign-ups. Sessions are cookies, so browser fetches, WebSocket upgrades, and native download links all carry identity automatically, and the `x-sandbox-user` header and the `?user=` query-parameter channel are deleted on both sides of the wire.

Built-in admin. At startup the backend ensures one stable bootstrap-admin identity exists and re-syncs its email, display name, password, role, and ban state from deployment configuration. Changing `ADMIN_EMAIL` updates that same identity rather than creating a second privileged account, changing `ADMIN_PASSWORD` rotates its credential, and a demoted or banned bootstrap admin heals on the next boot. Published development credentials require an explicit opt-in, a loopback public origin, and a loopback-only listener; every other startup refuses to run without an explicit public origin, auth secret, and bootstrap credentials.

Status, and the standalone ban. Status is derived, never stored as its own column, from the `role` Better Auth's admin plugin maintains. Because the plugin stores `role` as a comma-splittable string, derivation reads the split list with a fixed precedence: `admin` present is `admin`, else `user` present is `normal`, else `pending`. A supported operation only ever writes one scalar role, so in practice role `admin` is `admin`, role `pending` is `pending`, and role `user` is `normal`. New GitHub sign-ups land `pending` because the admin plugin's default role is set to `pending`, a role the deployment declares in its access-control config. `banned` is a standalone flag, not a status that overrides role: a banned user cannot sign in and their existing sessions are revoked at ban time, which is the admin plugin's own behavior, so a banned user never authenticates and never reaches the guards. Pending users can sign in and browse everything public but cannot start sessions, submit, or rate, and they see an awaiting-approval notice. Read-only routes stay open to anonymous visitors exactly as they are today.

Authorization matrix. A `normal` or `admin` user may start sessions, submit, and rate. An `admin` alone passes the `/api/admin` guard and the operator-only reads. The Stage 3 identity seam in `backend/src/identity.ts` is rewritten around an asynchronous cookie-session lookup and a small set of shared guards, `requireUser`, `requireActive`, and `requireAdmin`. The allowlist predicates and the orchestrator's allowlist check are deleted, and the operator persona keeps its name and its `not_operator` wire code while its source of truth becomes `status === 'admin'`.

Admin user management. The roster is driven through the admin plugin's own endpoints under `/api/auth/admin/*`, which are gated server-side by the plugin's custom-role permission checks: list with search and pagination, create a user with a fixed email and password, set role to approve a pending user or to promote and demote, ban with a reason, unban, and reset a password. The custom admin role deliberately omits user deletion, so the plugin refuses its remove-user endpoint and attribution cannot be orphaned through a direct API call. A new admin-only Users page in the frontend drives the permitted operations through the Better Auth Vue client, so the stage needs no bespoke roster routes on the app's own API.

Frontend. A `/login` page carries the email and password form and, when configured, the GitHub button. The sidebar account block gets a real sign-out. `GET /api/me` is reshaped around the session user and its status, `frontend/src/identity.ts` is deleted because cookies replace the header and query-parameter identity everywhere, and the shell gains the pending-approval banner and the signed-out affordances anonymous browsing needs.

GitHub integration. Step 6 connects a GitHub sign-in to an existing account with the same verified email instead of creating a duplicate pending user. The profile page provides an explicit connect and disconnect flow, the GitHub username appears on the profile and account menu alongside the avatar GitHub sign-ups already carry, and an agent profile links to its owner's GitHub. The policy details live in the subplan.

## Done when

A fresh deployment refuses to start until auth secrets and the bootstrap-admin password are configured, then starts with only that admin able to sign in. Changing the configured admin email or password and restarting updates the same stable identity without leaving the old credential privileged. A visitor browses environments, replays, docs, and leaderboards anonymously. A new user signs in with GitHub, lands `pending`, sees the awaiting-approval notice, and is refused when trying to start a session, submit, or rate. The admin opens the Users page, finds the pending user by an email search, and approves them, and the user, now `normal`, starts a session, submits, and rates, all attributed to their Better Auth user id. The admin bans a user, whose live session cookie stops working on its next request and who can no longer sign in, and unbanning restores access. The admin creates an email and password account manually and promotes a user to admin, who can then reach `/api/admin` and the admin pages. Public self-registration and user deletion do not exist through either the UI or an accepted API operation. `SESSION_ALLOWLIST` and `OPERATOR_ALLOWLIST` appear nowhere in code, tests, or docs. For step 6: a GitHub sign-in whose verified email matches an existing account signs into that account rather than creating a pending duplicate, a signed-in user connects and disconnects a GitHub account from their profile page, the profile and account menu show the GitHub username, an agent profile links to its owner's GitHub, and disconnecting the only sign-in method is refused.
