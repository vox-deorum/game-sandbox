It grows the minimal Stage 5 `iterations` record into full per-iteration configuration. ## What Stage 5 already built

[Stage 5.1](../stage-05/1-storage-and-iteration-seed.md) created `iterations` (`id`, `env_id`, `deps_version`, `status` = `open`|`closed`, `created_at`), seeded one per environment at startup, plus `submissions`, `submission_checks`, and `session_submissions`. It deliberately kept the iteration columns small so this stage could extend them rather than rewrite them. This step keeps the seed working. An already-seeded Stage 5 iteration migrates to an `unreleased`, submission-`open`, play-`open` iteration with an empty default match design, so local submissions and watch/play continue to work. New operator-declared iterations start `unreleased`, submission-`closed`, and play-`closed`. Opening submissions preserves the existing one-open-submission-iteration-per-environment invariant.

## Schema

All tables live in the single Kysely schema (`backend/src/storage/schema.ts`), the one source of truth from [stage-03/backend-skeleton-and-storage.md](../stage-03/backend-skeleton-and-storage.md). Nothing declares tables or queries outside `storage/`. Add the string-literal unions and table interfaces, register them on the `Database` interface, and derive domain types (`Iteration = Selectable<IterationsTable>`, etc., with `Insertable`/`Updateable` where an operation needs them).

### `iterations` - extended

Keep the Stage 5 columns. Rename and add columns for the three public gates and the configuration. The submission window, public play window, and release status are independent, so model them as separate columns rather than overloading one `status`. Their independence matters: a user can see an iteration when any one of them is in effect (submissions open, play open, or results released), and each column gates a different public surface.

- `submission_status` (`open`|`closed`): the Stage 5 `status`, renamed for clarity. It controls whether the submission form accepts agents. The migration renames the existing column, drops `iterations_open_unique`, and recreates it as a partial unique index on `(env_id) WHERE submission_status = 'open'`, so only one iteration per environment can accept submissions at once.
- `play_status` (`open`|`closed`): controls whether ordinary signed-in, allowlisted users can start public watch/play sessions for this iteration and write or update ratings against it. Play is independent of release status. The operator can open play on an iteration whose results are still `unreleased`, so users can watch and play it before its boards go public. Seeded Stage 5 rows start `open` for local continuity; operator-created rows start `closed`. Add a partial unique index on `(env_id) WHERE play_status = 'open'`, so only one iteration per environment is the default public play target.
- `release_status` (`unreleased`|`released`): controls whether the iteration's results — its boards and history — are shown to users outside the operator console. They stay operator-only until released, then appear on the environment page and in history. Seeded iterations start `unreleased`.
- `label` (text, nullable): an operator-facing name for the iteration ("Week 3", "Final round"). The admin console and history list show it.
- `deps_version` is no longer its own column. It is just another configuration value, so it folds into `config` (below). It is the pinned template dependency-set version, defaulting to the latest template release at declaration (the current `DEPS_VERSION`), per [submission.md](../../docs/specs/submission.md). The Stage 6 migration copies the existing Stage 5 `deps_version` column value into the `config` document and then drops the column. The Stage 5 submit-route reader is updated to read `config.deps_version` in this change set.
- `config` (text, JSON): the structured iteration configuration (below), stored as one validated JSON document rather than spread across columns. It is a nested, evolving shape (match design, override blocks) that the admin API and the workflow read and write whole, never by field. A typed `IterationConfig` codec (parse + serialize, rejecting unknown keys) is the single gate; the column never holds unvalidated text.
- `created_at` (unchanged), `released_at` (nullable, stamped on first release for history ordering).

Operator-created iterations are `unreleased`, submission-`closed`, and play-`closed` by default. The only exception is the migrated Stage 5 seed row, which stays submission-`open` and play-`open` for local continuity. Opening submissions fails with a typed conflict if another iteration for the same environment already accepts submissions; closing that other iteration is an explicit step. Opening public play fails with a typed conflict if another iteration for the same environment is already play-open, regardless of either iteration's release status.

Decision recorded here: `config` is a JSON document, not normalized into `match_configurations`/`overrides` tables. The match design is small (a handful of slot compositions), authored and read as a unit, and has no row-level query needs. A JSON column keeps the schema flat and lets the shape evolve without a migration per field (messaging/LLM overrides land inert now and activate in Stages 8/9). The run results below _are_ normalized, because those are queried per-agent for the board.

`IterationConfig` shape (the typed codec, documented here so the admin API in step 3 and the scheduler in step 2 share one definition):

- `deps_version`: the pinned template dependency-set version every submission in the iteration is built and run against, defaulting to the latest template release at declaration. It lives inside `config` so that a run's `config_snapshot` is the single frozen record of everything that governed the run (there is no separate `deps_version_snapshot`).
- `matches`: a list of match configurations. Each has `slots` (an ordered list of seat specs, each `builtin-naive` or `submission`), `seeds` (a non-empty list of integers passed to both env and agents), and `games` (a positive per-configuration game count the scheduler uses; see step 2). Every saved match configuration must assign at least one slot, and the admin API validates the slot count against the environment's metadata. For Flappy Bird, a single match with one `submission` slot is the norm. Multi-slot compositions (`[naive, naive, naive, submission]`) are valid and forward-compatible with Stage 7 opponents. A whole iteration may temporarily have an empty `matches` list while it is still unconfigured, but the workflow trigger refuses to run an empty design.
- `overrides`: an optional block with `step_timeout_ms` and `episode_timeout_ms` (effective this stage; they fall back to environment defaults from [environment.md](../../docs/specs/environment.md) when absent), plus the parsed-but-inert `messaging` (length cap / disable) and `llm` (model allowlist, token/call/rate budgets) blocks. The codec validates and stores those inert blocks so the format is stable before Stages 8/9 consume them. The operator's iteration-wide rating prompt is **not** part of `config`. It is display-only human-feedback guidance, read live at rating time and never from a run's `config_snapshot`, and the operator must be able to set or adjust it at any point in the iteration's life. Editing `config` once a workflow run exists is a destructive, force-confirmed action (step 3 — it deletes the existing runs and boards). So folding the prompt into `config` would mean you could not tweak display-only rating guidance without wiping results. It is therefore its own always-editable column:

- `rating_prompt` (text, nullable, length-capped): the operator's iteration-wide rating prompt shown to human raters for every agent in the iteration (see step 6 and [leaderboard.md](../../docs/specs/leaderboard.md)). Null or empty means no iteration prompt. It is editable regardless of submission window, play window, release status, or whether runs exist, since it never affects workflow execution.

### `sessions` - iteration attribution

Add nullable `iteration_id` to the existing `sessions` table, back-filled to null for old rows. Stage 6 writes it for every new rateable watch or play session from an explicit iteration target, never by guessing from the open submission iteration:

- A public submitted-agent watch session resolves the iteration from the selected submission, or from an explicit `iteration_id` if the API includes one. The submission must belong to that iteration, be active/ready there, and the iteration must be play-`open` for non-operators.
- A public Naive-only watch session or human play session resolves the environment's current play-open iteration. If none exists, the route refuses the public launch with `no_play_open_iteration`.
- An operator admin dry run may name an iteration that is not play-open (for example an unreleased one). That session is not public-rateable unless the iteration later meets the normal play-open rule at rating time.

This is the iteration key that ratings use later. Old rows with null `iteration_id` cannot receive ratings, because their competition boundary is unknown. Closing an iteration's play window stops new public sessions and new rating writes for that iteration, but does not delete existing sessions or ratings.

### Agent identity

Use one agent identity shape everywhere this stage stores or returns an agent: `AgentRef = { kind: 'submission', submission_id, user_id } | { kind: 'builtin-naive' }`. Tables that need filtering or grouping store it in concrete columns, not opaque JSON: `agent_kind` (`submission`|`builtin-naive`), `agent_submission_id` nullable, and `agent_user_id` nullable. For `builtin-naive`, both nullable columns are null. For a submitted agent, both are required. Scheduled slots, `game_results`, `automated_placements`, ratings, board payloads, and rating payloads all use this exact shape.

### `iteration_runs` - one workflow execution

The automated workflow can run more than once per iteration (the re-run requirement), and each run replaces the iteration's board. Model the run explicitly, so that a re-run is a new run row and the board always points at the latest completed one:

`iteration_runs`: `id` (text, backend-generated), `iteration_id`, `requested_by` (operator identity), `config_snapshot` (validated `IterationConfig` JSON, which now includes `deps_version`, copied from the iteration when the run is created), `submission_snapshot` (JSON array of the active `ready` submitted-agent refs eligible when the operator triggered the run), `status` (`RunStatus`: `pending`, `running`, `completed`, `failed`, `cancelled`), `started_at`, `ended_at` (null while running), `error` (nullable text for a run-level failure). The admin status view and log stream key off this row. The trigger builds the concrete schedule from these snapshots and persists it to `iteration_run_games` before enqueueing the runner. The runner reads the persisted games, not the mutable `iterations` or `submissions` rows, so editing an iteration or resubmitting after the trigger cannot change what the run executes.

### `iteration_run_games` - one scheduled match

`iteration_run_games`: `id`, `run_id`, `match_index` (which `config_snapshot.matches` entry produced it), `game_index` (the deterministic schedule index within the run), `seed`, `slots` (JSON array of resolved `AgentRef` values, one per seat), `status` (`GameStatus`: `pending`, `running`, `completed`, `failed`, `timed_out`, `cancelled`), `recording_id` (nullable FK into the Stage 4 recordings, set when the run records; this is the per-row replay link the board exposes), `started_at`, `ended_at`, `error`. The workflow trigger writes these from the pure scheduler before enqueueing step 4. The runner only advances statuses and fills recordings/results. The board (step 5) aggregates them. `game_index` is also the tie-breaker for representative replay selection.

### `game_results` - per-slot outcome of a game

This table is normalized so the board can aggregate per agent without incorrectly averaging per-game means. `game_results`: `id`, `game_id` (FK `iteration_run_games`), `slot_index`, `agent_kind`, `agent_submission_id`, `agent_user_id`, `episode_score` (the normalized higher-is-better leaderboard score from the recording), `agent_compute_ms_total` (the sum of `decision_ms + learn_ms` now, with future `chat_ms` and LLM wait included when those hooks land), `acted_tick_count` (the number of ticks that contributed to that total), `failed` (boolean: the agent crashed or timed out but a score row exists), and `failure_reason` (nullable text). There is one row per participating seat per game, when a result can be attributed to a specific agent. Neither `agent_compute_ms_total` nor `acted_tick_count` is a single recorded harness field. Step 4's runner derives them from the recording's per-tick records: it sums each tick's `decision_ms + learn_ms` (treating `learn_ms` as zero where it is absent, as for the non-learning Naive baseline, which emits no learn hook) and counts the ticks that carry that slot's timing as `acted_tick_count`. The automated board computes mean per-decision time as `sum(agent_compute_ms_total) / sum(acted_tick_count)` across the run, with a null or blank value if the count is zero. An infrastructure failure, such as a container that never starts or an unreadable recording, marks the game failed but does not invent a `game_results` row.

### `automated_placements`

Persist only the per-agent placement snapshot that profiles and history need, not full board rows. `automated_placements`: `iteration_id`, `env_id`, `run_id`, `rank`, `agent_kind`, `agent_submission_id`, `agent_user_id`, `mean_score`, `mean_agent_compute_ms`, `failure_count`, `recording_id`, `created_at`. Submitted-agent rows are unique on `(iteration_id, agent_kind, agent_submission_id)`. The Naive row has a null `agent_submission_id`, so add a second partial unique index on `(iteration_id, agent_kind) WHERE agent_kind = 'builtin-naive'`. Placement rows are rewritten when a new completed run supersedes the prior completed run.

### `ratings`

`ratings`: `id`, `iteration_id`, `env_id` (denormalized for lookups), `rater_user_id` (the resolved identity from the Stage 4 seam), `agent_kind`, `agent_submission_id`, `agent_user_id`, `score` (integer 1-5), `created_at`, `updated_at`. A unique index on `(iteration_id, rater_user_id, agent_kind, agent_submission_id)` enforces one effective rating per user per agent per iteration. SQLite treats nulls as distinct, so add a second partial unique index on `(iteration_id, rater_user_id, agent_kind) WHERE agent_kind = 'builtin-naive'` for the Naive row. Re-rating is an upsert that overwrites `score` and `updated_at`. Ratings of the user's own submitted agent (`agent_kind = 'submission'` and `rater_user_id == agent_user_id`) are rejected at the storage/route layer and never inserted. The Naive baseline has no owner and is rateable.

### `agent_rating_prompts`

The author-set rating prompt is the second of the two prompts a rater sees (the first is the operator's `iterations.rating_prompt`). It is the agent author's own statement of what to evaluate. It is settable and editable after submission, so it is **not** part of the pinned, validated submission artifact and does not live on the `submissions` row. Store it in its own table, keyed per agent-author per iteration, so it survives resubmission within the iteration. (A participant has one agent per iteration; the prompt is about that agent, not a specific commit.)

`agent_rating_prompts`: `iteration_id`, `env_id` (denormalized), `user_id` (the author's resolved identity), `prompt` (text, length-capped), `updated_at`. Unique on `(iteration_id, user_id)`. Only submitted agents have authors, so the Naive baseline never has a row here; when rating Naive, only the iteration prompt applies. The rating read (step 6) resolves a submitted agent's author prompt by `(iteration_id, submission.user_id)`, independent of which `agent_submission_id` ratings key on, so a resubmission does not drop the author's prompt.

## Migration

One new ordered TypeScript migration module under the storage package, run on startup through Kysely's `Migrator` exactly as the earlier stages established (no migration CLI; deployment is "start the process"). It renames `iterations.status` to `submission_status`. It drops and recreates the open-submission partial unique index on `(env_id) WHERE submission_status = 'open'`. It adds `play_status`, `release_status`, `label`, `config`, `rating_prompt`, and `released_at` to `iterations` (with `play_status` defaulting `open` for already-seeded rows, `release_status` defaulting `unreleased`, `config` defaulting an empty-matches document that carries the row's existing `deps_version` for already-seeded rows, and `rating_prompt` null). It folds the Stage 5 `deps_version` column into `config.deps_version` and then drops the standalone `deps_version` column. It adds the partial unique index on `(env_id) WHERE play_status = 'open'`. It adds nullable `iteration_id` to `sessions`. It creates `iteration_runs`, `iteration_run_games`, `game_results`, `automated_placements`, `ratings`, and `agent_rating_prompts`. Finally, it adds the hot-read indexes: `iteration_runs(iteration_id)`, `iteration_run_games(run_id, game_index)`, `game_results(game_id)`, `game_results(agent_kind, agent_submission_id)`, `automated_placements(agent_kind, agent_submission_id, env_id)`, `ratings(iteration_id, agent_kind, agent_submission_id)`, the unique `agent_rating_prompts(iteration_id, user_id)`, plus the placement and rating unique indexes described above. It is additive over the Stage 3/4/5 migrations and rewrites no existing rows beyond back-filling the new nullable or defaulted columns.

Recording retention is handled by an explicit storage query rather than by overloading `recordings.user_id`. Add `listProtectedLeaderboardRecordingIds()` (or an equivalent internal retention helper) that returns the recording ids referenced by the latest completed run of every viewable iteration (a `released` one, or an `unreleased` one an operator is still working on). The retention sweep exempts that set from the live-session age and quota passes. Workflow recordings from superseded runs fall outside the set and can be reclaimed.

## Storage interface

Extend the `Storage` interface (`storage/index.ts`) and its Kysely implementation (`storage/kysely/`) with domain-shaped methods, never exposing SQL:

- Iterations and sessions: `getIteration(id)` (already added in Stage 5.5); `getOpenSubmissionIteration(envId)` / `ensureOpenIteration` (the Stage 5 `getOpenIteration`, renamed for its public meaning now that "open" is ambiguous across the two windows; the existing Stage 5 submit-route caller is updated to the new name in this change set); `getPublicPlayIteration(envId)` (the play-open target for public watch/play); `createIteration(input)` (admin declare: a new `unreleased`, submission-`closed`, play-`closed` iteration whose config — including `deps_version` — defaults to the current release); `updateIterationConfig(id, config, { force })` (replaces the whole `IterationConfig`, including `deps_version`; with no runs and no `deps_version` change it just writes, otherwise it needs `force`, which first deletes the iteration's runs via `deleteRunsForIteration`, and, when `deps_version` changed and submissions exist, deletes the iteration's submissions via `deleteSubmissionsForIteration`; step 3 surfaces this override path as a UI confirmation); `setSubmissionStatus(id, open|closed)` (returns a typed `open_iteration_exists` conflict when opening would violate the one-open submission invariant); `setPlayStatus(id, open|closed)` (returns `open_play_iteration_exists` when opening public play would violate the one-play-open invariant); `setReleaseStatus(id, unreleased|released)` (stamps `released_at` on first release); `listIterations(envId, { includeUnreleased })` (history, newest first; public reads pass `includeUnreleased: false`, admin reads pass `true`); `getReleasedIteration(envId)` (the latest released iteration for the environment, ordered by `released_at`); and `setSessionIteration(sessionId, iterationId)`, or a `createSession` input extension that writes the nullable `iteration_id`.
- Runs and games: `createRunWithSchedule(iterationId, requestedBy, submissionSnapshot, scheduledGames)` snapshots the iteration config (which now includes deps version), eligible submissions, and concrete games into the run row plus `iteration_run_games`, all in one transaction. `deleteRunsForIteration(iterationId)` (used by the forced config edit to clear an iteration's runs, games, results, and placements). `setRunStatus(id, status, error?)`, `getLatestRun(iterationId)` and `getLatestCompletedRun(iterationId)`, `listRunGames(runId)`, `setRunGameStatus(...)`, `attachRunGameRecording(gameId, recordingId)`, `recordGameResult(...)`, and `listGameResultsByRun(runId)`.
- Placements and boards: `replaceAutomatedPlacements(iterationId, runId, rows)`, `listPlacementsByAgent(agentRef, envId?)`, and `getAutomatedBoard(iterationId)` as a service/storage helper over latest-completed-run results.
- Ratings: `upsertRating(input)` (accepts `AgentRef`, enforces own-agent exclusion for submissions, and uses the unique indexes as an upsert), `getRating(iterationId, raterUserId, agentRef)`, and `listRatingsByIteration(iterationId)` / `aggregateRatingsByAgent(iterationId)` for the human board.
- Rating prompts: `setIterationRatingPrompt(iterationId, prompt)` (the operator's iteration prompt, editable anytime, independent of the `config` immutability rule); `upsertAgentRatingPrompt(iterationId, userId, prompt)` (the author's set or edit, keyed by `(iteration_id, user_id)`); `getAgentRatingPrompt(iterationId, userId)`; and `listAgentRatingPromptsByIteration(iterationId)`, so the rating read in step 6 can attach each submitted agent's author prompt. The iteration prompt comes back on `getIteration` as the `rating_prompt` column.
- Retention: `listProtectedLeaderboardRecordingIds()` returns current-run leaderboard recording ids for viewable iterations so the Stage 4 retention sweep can exempt them.

## Operator allowlist seam

The admin API (step 3) gates on operator identity. Add a small `isOperator(identity)` helper alongside the existing identity seam (`backend/src/identity.ts`), following the same shape the session allowlist already uses. A config field (`backend/src/config.ts`) `operatorAllowlist` reads from an `OPERATOR_ALLOWLIST` env var, defaulting to `[DEV_USER_ID]` exactly as `sessionAllowlist` does. `isOperator(identity)` is implemented over the existing `isAllowlisted(userId, allowlist)` helper rather than as a new build-mode special case. So the console works out of the box in dev (the mock `dev-user` is in the default list), and a real deployment lists its operator handles, checked against the resolved GitHub identity once OAuth lands. This is the single authorization predicate every admin route and the admin-only iteration reads consult. It does not change the Stage 4 identity resolution itself; it only adds the operator predicate over it.

## Tests

Vitest against the real Kysely implementation on better-sqlite3 `:memory:`, no Docker:

- The migration renames `status` to `submission_status`, recreates the one-open-submission partial unique index on the renamed column, adds `play_status` with the play-open conflict index, adds the new iteration/session columns with defaults, and creates the six new tables and the indexes. A second `Migrator` run is a no-op. An already-seeded Stage 5 iteration survives as `unreleased` with `submission_status: open`, `play_status: open`, and an empty match design.
- `createIteration` writes an `unreleased`, submission-`closed`, play-`closed` iteration whose validated config carries the current `deps_version`. `updateIterationConfig` round-trips the `IterationConfig` codec and rejects an unknown key, empty match slots, zero games, empty seeds, or a malformed match design. A forced config edit deletes the iteration's existing runs; a forced `deps_version` change additionally deletes its existing submissions; and an unforced edit against existing runs (or a deps change against existing submissions) is refused.
- `setSubmissionStatus`, `setPlayStatus`, and `setReleaseStatus` flip the three gates independently (play can be opened on an `unreleased` iteration). Opening submissions while another environment iteration is open for submissions returns `open_iteration_exists`. Opening public play while another iteration is play-open returns `open_play_iteration_exists`. `setReleaseStatus('released')` stamps `released_at` once and leaves it stable on a re-release. `getReleasedIteration` ignores unreleased iterations, and `listIterations({ includeUnreleased: false })` hides unreleased boards/history while still letting the submit route find an open submission iteration.
- `createSession` or `setSessionIteration` records a nullable `iteration_id`. Public Naive/human sessions attach to the current play-open iteration, submitted-agent sessions attach to the selected submission's iteration after validating it is public-playable, and old null rows cannot be rated.
- `createRunWithSchedule` snapshots config (including deps), requested_by, and eligible submissions, and stores deterministic `game_index` plus resolved `AgentRef` slots before the runner starts. `recordGameResult` round-trips the concrete agent columns plus `agent_compute_ms_total` and `acted_tick_count`. `getLatestCompletedRun` returns the most recent `completed` run and ignores a later `running`/`failed` one; this is what the board reads, so a failed re-run does not blank a good board.
- `attachRunGameRecording` links a game to a Stage 4 recording so the board row can deep-link a replay.
- `replaceAutomatedPlacements` rewrites placement rows for a completed re-run and supports both submitted agents and the Naive baseline.
- `upsertRating` inserts a 1-5 rating for a submitted agent or the Naive baseline. A second rating by the same user for the same agent overwrites rather than duplicating. A rating of the user's own submitted agent is rejected, Naive is rateable, and `aggregateRatingsByAgent` returns mean and count per agent ref.
- `setIterationRatingPrompt` sets and clears the operator's `rating_prompt` and remains editable after a run exists (unlike `updateIterationConfig`). `upsertAgentRatingPrompt` inserts then overwrites an author's prompt keyed by `(iteration_id, user_id)`, and it survives a simulated resubmission (a new `agent_submission_id` for the same user still resolves the same prompt). `listAgentRatingPromptsByIteration` returns one prompt per author.
- `listProtectedLeaderboardRecordingIds` exempts only current-run recordings for viewable iterations and excludes superseded-run recordings.
- `isOperator` resolves the dev mock user as operator and honors a configured allowlist.

The storage suite proves the config codec, the one-open submission invariant, the one-play-open invariant, the three-gate lifecycle, trigger-time roster and schedule snapshots, session iteration attribution, latest-completed-run selection, placement rewrites, the rating upsert/own-agent/Naive rules, both rating prompts (the operator's stays editable after a run, the author's survives resubmission), leaderboard-recording retention protection, and the operator predicate on `:memory:`.
