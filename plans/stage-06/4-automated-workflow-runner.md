# Stage 6.4: Automated Workflow Runner

Status: not started.

Part of [Stage 6](../stage-06-leaderboards.md). This is build-order step 4: the background runner that takes a triggered `iteration_runs` row, executes its scheduled games sequentially on one host through the Stage 3 execution driver, records every run, captures container logs for the admin stream, aggregates timing from the recordings, and drives the run to a terminal state. This is the Docker-gated heart of the stage.

## Position in the pipeline

The admin trigger route (step 3) creates a `pending` run with `config_snapshot` (which now includes the deps version), `requested_by`, a trigger-time `submission_snapshot`, and the already-resolved `iteration_run_games` rows, then enqueues it here. The runner loads those persisted games and executes them in order. It never rebuilds the schedule or re-reads active submissions, so a resubmission after trigger cannot change the run. It reuses the Stage 3 driver and the Stage 5 submission overlay images. The board computation (step 5) reads the `game_results` this runner writes.

**Shared launch seam (a real new path, factored to avoid divergence).** The existing launch glue (`backend/src/session/orchestrator.ts`, `backend/src/session/live-session.ts`) is built for a _live, browser-attached_ session: it assumes an attached socket, human timeouts, and the WebSocket bridge. The runner needs **headless run-to-completion** — drive a container to exit, then read the recording it produced — which that path does not provide. So this is honestly a second caller of the driver, and the plan handles that by **extracting the config-assembly and image-resolution logic the orchestrator already has into a shared helper** (the slot-binding-to-session-config mapping, the `ensureSubmissionImage`/built-in-agent resolution, the `players` attribution build) that both the live session and the runner call. The runner adds only the headless concerns on top: no socket, no human timeout, wait for container exit, then read back the recording. The goal is one config-assembly path, not two that drift; the runner is new orchestration, but not a duplicated config builder.

## Execution model

Per [leaderboard.md](../../docs/specs/leaderboard.md):

- **Sequential, single host.** Games run one at a time so wall-clock timing is comparable across agents (the spec's explicit reason; at class scale the serialization cost is small). The runner is concurrency-1 over games within a run, like the Stage 5 validation worker is concurrency-1 over submissions.
- **One container per match.** Each game runs in its own container holding the harness, the environment, and the agent(s), launched through the Stage 3 driver via the shared launch helper above. For a submission seat the runner uses that submission's built overlay image (Stage 5.4, resolved through `ensureSubmissionImage`); for a `builtin-naive` seat it uses the same built-in agent the watch picker launches. Single-agent Flappy Bird is one agent in the single slot; multi-submission-seat execution is rejected by the scheduler until Stage 7, but the runner stores and passes the resolved `AgentRef` slots assignment so the stored run shape does not change later.
- **Seeds to env and agents.** The scheduled game's seed is passed to both the environment reset and the agents, per [environment.md](../../docs/specs/environment.md), so a deterministic agent reproduces its run exactly on a re-run.
- **Timeouts.** Per-step and per-episode timeouts come from the environment defaults unless the iteration's `overrides` set them (step 1 config). The harness already enforces per-step/per-episode limits; the runner passes the effective values in. A slow or stuck agent trips the timeout and does not block the queue.
- **Recording.** Every game is recorded to the shared recordings store (the same Stage 4 path and JSONL format, written to the volume mounted into the workflow container per [recording.md](../../docs/specs/recording.md)). The runner registers a recording row, attaches the resulting `recording_id` to the `iteration_run_games` row (`attachRunGameRecording`), and relies on the step-1 retention helper to exempt current-run leaderboard recordings from live-session eviction. The recording row's `user_id` is the natural owner of that game: for a submission seat's game, the submission's owner; for a Naive-baseline game, the run's `requested_by` operator (the only human associated with an automated baseline run). `pinned` is left `false` — these recordings are kept by the explicit `listProtectedLeaderboardRecordingIds()` retention path (step 1/5), not by the per-user pin mechanism, so they never count against a user's pin quota. The recording header carries the per-slot attribution (which submission / the Naive agent) already defined by [recording.md](../../docs/specs/recording.md).

## Per-game outcome and the failing-agent rule

When a game finishes, the runner reads the recording it just produced and writes one `game_results` row per participating seat:

- `episode_score` - the environment's leaderboard score for that slot, normalized higher-is-better (Flappy Bird is already higher-is-better; the normalization contract is the environment's, per [leaderboard.md](../../docs/specs/leaderboard.md)). The score comes from the recorded per-step `score` the harness emits, using the final score for that slot when at least one readable state exists. With Flappy Bird the only environment this stage, the normalization is identity (the final `score` as-is); implement it behind a per-environment seam (a function from raw final score to leaderboard score) rather than scattering the assumption, so a future lower-is-better environment supplies its own mapping without touching the board math.
- `agent_compute_ms_total` and `acted_tick_count` - aggregated from the recorded per-agent timing fields the harness already writes (`agents[slot].timing.decision_ms` and `.learn_ms` on each per-tick state). For Stage 6 the per-tick compute contribution is `decision_ms + learn_ms`; the runner sums those contributions across the recording and counts the per-tick records that carry that slot's timing as `acted_tick_count`. Note `learn_ms` is present only for learning agents — the Naive baseline emits no learn hook — so the runner treats an absent `learn_ms` as zero, and there is no single recorded "acted tick count" field to read: it is the count of timing-bearing ticks the runner derives. When `chat_ms` and LLM wait timing land in later stages, they are added to the same per-tick compute total. The runner aggregates; it does not re-measure.
- `failed` - true when the agent crashed or timed out and the runner can still attribute a result row to that agent. The row uses the final recorded score when present, rather than inventing a replacement score, and surfaces `failure_reason`. In Stage 6's single-slot workflow, a container exit after a readable header/state for a submitted or Naive slot is attributable to that slot; the same per-slot rule extends to multi-agent runs in Stage 7. A single agent failure never aborts the remaining scheduled games. The `iteration_run_games.status` records `failed`/`timed_out` for that game while `game_results.failed` marks the specific seat.

A game whose container fails to start, produces no readable recording header, or produces an unreadable recording is an infrastructure fault. It marks the game `failed` with an error, writes no invented `game_results` row, and is distinguished from an agent fault in the run log, so the operator can tell "your agent crashed" from "the host hiccuped."

## Logs and progress for the admin stream

As each game runs, the runner emits events the step-3 WebSocket log route relays: a game-started line (which seats, which seed), the match container's stdout/stderr lines (reusing the Stage 3 line-splitting transport, `pumpLines`, so the byte-stream-to-lines plumbing is not reinvented), and a game-finished line with its status and scores. The existing transport streams live only, and this step keeps it that way — **the per-run backlog buffer is deferred** (a late subscriber misses lines emitted before it attached). Game-status transitions (`pending` to `running` to terminal) are written to storage, so the admin status view reflects progress even without an attached stream, and a console attaching mid-run renders progress from those persisted statuses while tailing live log lines. A buffered backlog can be added later as an in-process per-run buffer if full mid-run scrollback is wanted; it is not a stage exit criterion.

## Re-run idempotency and cancellation

- **Re-run replaces.** Triggering a new run for an iteration creates a new `iteration_runs` row, a fresh config/deps snapshot, and a fresh set of games; the board (step 5) always reads the latest _completed_ run, so a re-run's results supersede the prior run's once it completes, while the prior run's rows remain until then (a failed or in-progress re-run never blanks a good released board). Recordings from a superseded run are eligible for the retention sweep (step 5) once they are no longer protected by the current-run helper.
- **Deterministic reproduction.** Because seeds are fixed by the schedule and passed through to env and agents, re-running the same config reproduces a deterministic agent's `episode_score` exactly, satisfying the stage's "re-running reproduces the scores of deterministic agents" exit criterion.
- **Cancellation.** A cancel request (step 3) sets a cooperative flag the runner checks between games; it stops scheduling further games, marks the in-flight game and the run `cancelled`, and tears down the current container through the driver. Mid-game cancellation is best-effort (let the current game finish or kill the container); the run does not produce a partial board, and a cancelled run is not the "latest completed" run.

## Tests

- **Docker-free (Vitest, FakeDriver):** with a fake driver that returns canned recordings, the runner loads the persisted `iteration_run_games`, executes them in order, writes `game_results` with expected scores plus `agent_compute_ms_total` and `acted_tick_count` parsed from fake `decision_ms` plus `learn_ms`, attaches recording ids, and reaches `completed`; an attributable crash/timeout with a readable partial recording produces a `failed` `game_results` row using the final recorded score without aborting the remaining games; an infrastructure-style driver error marks that game `failed` with an error and writes no result row; a cancel flag set mid-schedule stops further games and marks the run `cancelled`; re-running creates a second run and `getLatestCompletedRun` returns it.
- **Docker-gated end-to-end (the real driver, gated like the Stage 5.4 build/load tests):** a small iteration with the worked Flappy Bird example as a submission plus the Naive baseline, two seeds, runs to completion, produces a recording per game with a valid header, and a deterministic example reproduces identical `episode_score` across two runs. This reuses the Stage 5 Docker-gated harness rather than standing up new container plumbing.

## Done when

Triggering a run launches the persisted scheduled games from the run snapshot sequentially on one host, records each with a replayable recording, aggregates the harness's score plus total agent compute timing and acted tick count into `game_results`, records attributable failing or timed-out agents without aborting the iteration, streams container logs to the admin console, and reaches a terminal run state. Re-running the same config reproduces deterministic agents' scores and, on completion, becomes the latest completed run the board reads. The board itself is computed in step 5.
