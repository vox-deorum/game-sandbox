# Stage 6.4: Automated Workflow Runner

Status: done. The Docker-backed `WorkflowRunner` (`backend/src/workflow/workflow-runner.ts`, behind the Stage 6.3 seam in `backend/src/workflow/runner.ts`) drains a `pending` run's persisted `iteration_run_games` one container at a time through the Stage 3 driver. It is **headless run-to-completion**: each game launches the live-runner entrypoint with an all-agent slot config and `headless: true` (no socket, no human source, no live pacing, so the container plays to its episode's end and exits as fast as the agents compute), the runner drains stdout (the tee'd recording lines plus the final `result` envelope) and stderr (relayed as `log` events), waits for exit, then attributes the outcome straight from the recording. Per game it registers the produced recording owned by the seat's natural owner (`createRecording`), attaches its id (`attachRunGameRecording`), and writes one `game_results` row per seat with normalized `episode_score`, plus `agent_compute_ms_total` and `acted_tick_count` aggregated from the recorded `decision_ms`/`learn_ms` (`backend/src/workflow/aggregate.ts`). The config-assembly that the live orchestrator and the runner share was extracted into `backend/src/session/launch-config.ts` (`assembleSeats`), so there is one slots/players path, not two; the per-environment higher-is-better normalization is a one-function seam in `backend/src/leaderboards/score.ts`. An attributable crash (non-zero exit/OOM) marks the game `failed`, a recorded `episode_limit` or runner wall-clock watchdog kill marks it `timed_out`, and either flags the seat while leaving the remaining games to run; a container that yields no readable recording header is an infrastructure fault (`failed`, no result row). A cooperative cancel flag stops scheduling, tears down the in-flight container, and settles the run `cancelled`. Runs execute one at a time (single host) via an in-process queue, and `onRunComplete` triggers the retention sweep. The harness `live.py` config grew optional `step_timeout_ms`/`episode_timeout_ms` and `headless` so the iteration's timeout overrides take effect while workflow games skip live cadence. Covered Docker-free by `backend/test/workflow/docker-runner.test.ts` (ordering, results/timing, headless launch config, watchdog timeout, attributable crash without aborting, recorded timeout, infrastructure fault, log/status relay, cancel, re-run, submission-overlay resolution and owner attribution) and Docker-gated end to end by `backend/test/integration/workflow-run.test.ts` (a worked example plus the Naive baseline over two seeds, valid recording headers, deterministic-score reproduction across two runs).

Part of [Stage 6](../stage-06-leaderboards.md). This is build-order step 4: the background runner. It takes a triggered `iteration_runs` row and executes its scheduled games sequentially on one host through the Stage 3 execution driver. It records every run, captures container logs for the admin stream, aggregates timing from the recordings, and drives the run to a terminal state. This is the Docker-gated heart of the stage.

## Position in the pipeline

The admin trigger route (step 3) creates a `pending` run, then enqueues it here. That run carries `config_snapshot` (which now includes the deps version), `requested_by`, a trigger-time `submission_snapshot`, and the already-resolved `iteration_run_games` rows. The runner loads those persisted games and executes them in order. It never rebuilds the schedule or re-reads active submissions, so a resubmission after the trigger cannot change the run. It reuses the Stage 3 driver and the Stage 5 submission overlay images. The board computation (step 5) reads the `game_results` this runner writes.

**Shared launch seam (a real new path, factored to avoid divergence).** The existing launch glue (`backend/src/session/orchestrator.ts`, `backend/src/session/live-session.ts`) is built for a _live, browser-attached_ session. It assumes an attached socket, human timeouts, and the WebSocket bridge. The runner needs **headless run-to-completion** instead: drive a container to exit, then read the recording it produced. That path does not provide this. So the runner is a second caller of the driver. The plan handles that by **extracting the config-assembly and image-resolution logic the orchestrator already has into a shared helper** that both the live session and the runner call. That helper covers the slot-binding-to-session-config mapping, the `ensureSubmissionImage`/built-in-agent resolution, and the `players` attribution build. The runner adds only the headless concerns on top: no socket, no human timeout, wait for container exit, then read back the recording. The goal is one config-assembly path, not two that drift. The runner is new orchestration, not a duplicated config builder.

## Execution model

Per [leaderboard.md](../../docs/specs/leaderboard.md):

- **Sequential, single host.** Games run one at a time so wall-clock timing is comparable across agents. This is the spec's explicit reason, and at class scale the serialization cost is small. The runner is concurrency-1 over games within a run, just as the Stage 5 validation worker is concurrency-1 over submissions.
- **One container per match.** Each game runs in its own container holding the harness, the environment, and the agent(s), launched through the Stage 3 driver via the shared launch helper above. For a submission seat, the runner uses that submission's built overlay image (Stage 5.4, resolved through `ensureSubmissionImage`). For a `builtin-naive` seat, it uses the same built-in agent the watch picker launches. Single-agent Flappy Bird is one agent in the single slot. The scheduler rejects multi-submission-seat execution until Stage 7, but the runner stores and passes the resolved `AgentRef` slots assignment, so the stored run shape does not change later.
- **Seeds to env and agents.** The scheduled game's seed is passed to both the environment reset and the agents, per [environment.md](../../docs/specs/environment.md). A deterministic agent therefore reproduces its run exactly on a re-run.
- **Timeouts.** Per-step and per-episode timeouts come from the environment defaults, unless the iteration's `overrides` set them (step 1 config). The harness enforces those limits once an agent call returns, and the runner also starts a per-game wall-clock watchdog derived from the effective episode timeout plus a short grace window. A slow or stuck agent therefore trips a timeout and does not block the queue.
- **Recording.** Every game is recorded to the shared recordings store, using the same Stage 4 path and JSONL format, written to the volume mounted into the workflow container per [recording.md](../../docs/specs/recording.md). The runner registers a recording row and attaches the resulting `recording_id` to the `iteration_run_games` row (`attachRunGameRecording`). It relies on the step-1 retention helper to exempt current-run leaderboard recordings from live-session eviction. The recording row's `user_id` is the natural owner of that game. For a submission seat's game, that is the submission's owner. For a Naive-baseline game, it is the run's `requested_by` operator, the only human associated with an automated baseline run. `pinned` is left `false`. These recordings are kept by the explicit `listProtectedLeaderboardRecordingIds()` retention path (step 1/5), not by the per-user pin mechanism, so they never count against a user's pin quota. The recording header carries the per-slot attribution (which submission, or the Naive agent) already defined by [recording.md](../../docs/specs/recording.md).

## Per-game outcome and the failing-agent rule

When a game finishes, the runner reads the recording it just produced and writes one `game_results` row per participating seat:

- `episode_score` - the environment's leaderboard score for that slot, normalized higher-is-better. Flappy Bird is already higher-is-better, and the normalization contract belongs to the environment, per [leaderboard.md](../../docs/specs/leaderboard.md). The score comes from the recorded per-step `score` the harness emits, using the final score for that slot when at least one readable state exists. Flappy Bird is the only environment this stage, so the normalization is identity (the final `score` as-is). Implement it behind a per-environment seam, a function from raw final score to leaderboard score, rather than scattering the assumption. A future lower-is-better environment then supplies its own mapping without touching the board math.
- `agent_compute_ms_total` and `acted_tick_count` - aggregated from the recorded per-agent timing fields the harness already writes (`agents[slot].timing.decision_ms` and `.learn_ms` on each per-tick state). For Stage 6 the per-tick compute contribution is `decision_ms + learn_ms`. The runner sums those contributions across the recording and sets `acted_tick_count` to the number of per-tick records that carry that slot's timing. `learn_ms` is present only for learning agents, since the Naive baseline emits no learn hook, so the runner treats an absent `learn_ms` as zero. There is no single recorded "acted tick count" field to read; the runner derives it as the count of timing-bearing ticks. When `chat_ms` and LLM wait timing land in later stages, they are added to the same per-tick compute total. The runner aggregates; it does not re-measure.
- `failed` - true when the agent crashed or timed out and the runner can still attribute a result row to that agent. The row uses the final recorded score when present, rather than inventing a replacement score, and surfaces `failure_reason`. In Stage 6's single-slot workflow, a container exit after a readable header or state for a submitted or Naive slot is attributable to that slot. The same per-slot rule extends to multi-agent runs in Stage 7. A single agent failure never aborts the remaining scheduled games. The `iteration_run_games.status` records `failed` or `timed_out` for that game, while `game_results.failed` marks the specific seat.

A game whose container fails to start, produces no readable recording header, or produces an unreadable recording is an infrastructure fault. The runner marks the game `failed` with an error and writes no invented `game_results` row. The run log distinguishes this from an agent fault, so the operator can tell "your agent crashed" from "the host hiccuped."

## Logs and progress for the admin stream

As each game runs, the runner emits events that the step-3 WebSocket log route relays: a game-started line (which seats, which seed), the match container's stdout/stderr lines, and a game-finished line with its status and scores. The container lines reuse the Stage 3 line-splitting transport, `pumpLines`, so the byte-stream-to-lines plumbing is not reinvented. The existing transport streams live only, and this step keeps it that way: **the per-run backlog buffer is deferred**, so a late subscriber misses lines emitted before it attached. Game-status transitions (`pending` to `running` to terminal) are written to storage. The admin status view therefore reflects progress even without an attached stream, and a console attaching mid-run renders progress from those persisted statuses while tailing live log lines. A buffered backlog can be added later as an in-process per-run buffer if full mid-run scrollback is wanted; it is not a stage exit criterion.

## Re-run idempotency and cancellation

- **Re-run replaces.** Triggering a new run for an iteration creates a new `iteration_runs` row, a fresh config and deps snapshot, and a fresh set of games. The board (step 5) always reads the latest _completed_ run. A re-run's results therefore supersede the prior run's once it completes, while the prior run's rows remain until then. A failed or in-progress re-run never blanks a good released board. Recordings from a superseded run become eligible for the retention sweep (step 5) once the current-run helper no longer protects them.
- **Deterministic reproduction.** Seeds are fixed by the schedule and passed through to env and agents, so re-running the same config reproduces a deterministic agent's `episode_score` exactly. This satisfies the stage's "re-running reproduces the scores of deterministic agents" exit criterion.
- **Cancellation.** A cancel request (step 3) sets a cooperative flag that the runner checks between games. The runner stops scheduling further games, marks the in-flight game and the run `cancelled`, and tears down the current container through the driver. Mid-game cancellation is best-effort: let the current game finish, or kill the container. The run does not produce a partial board, and a cancelled run is not the "latest completed" run.

## Tests

- **Docker-free (Vitest, FakeDriver):** a fake driver returns canned recordings. The runner loads the persisted `iteration_run_games`, executes them in order, writes `game_results` with expected scores plus `agent_compute_ms_total` and `acted_tick_count` parsed from fake `decision_ms` plus `learn_ms`, attaches recording ids, and reaches `completed`. It verifies that launch configs are headless and carry timeout overrides. An attributable crash, recorded timeout, or wall-clock watchdog timeout with a readable partial recording produces a `failed` `game_results` row using the final recorded score, without aborting the remaining games. An infrastructure-style driver error marks that game `failed` with an error and writes no result row. A cancel flag set mid-schedule stops further games and marks the run `cancelled`. Re-running creates a second run, and `getLatestCompletedRun` returns it.
- **Docker-gated end-to-end (the real driver, gated like the Stage 5.4 build/load tests):** a small iteration runs to completion. It uses the worked Flappy Bird example as a submission plus the Naive baseline, with two seeds. It produces a recording per game with a valid header, and a deterministic example reproduces identical `episode_score` across two runs. This reuses the Stage 5 Docker-gated harness rather than standing up new container plumbing.

## Done when

Triggering a run launches the persisted scheduled games from the run snapshot sequentially on one host. The runner records each game with a replayable recording. It aggregates the harness's score plus total agent compute timing and acted tick count into `game_results`. It records attributable failing or timed-out agents without aborting the iteration. It streams container logs to the admin console and reaches a terminal run state. Re-running the same config reproduces deterministic agents' scores, and on completion it becomes the latest completed run the board reads. The board itself is computed in step 5.
