# Stage 6.3: Admin HTTP API and Operator Gating

Status: not started.

Part of [Stage 6](../stage-06-leaderboards.md). This is build-order step 3: the operator-only admin HTTP routes. They declare and configure iterations, control the submission window, the public play window, and release status, trigger and re-run the workflow, inspect status, and stream the running workflow's container logs. These routes are the **stable contract** of the stage. The admin console (step 7) is the primary client, but the same routes are scriptable for headless deploys. This is the agreed "admin HTTP API is the contract" decision. No file-based CLI is built.

## Operator gating

Every route here is gated by the `isOperator(identity)` predicate from step 1. The identity comes from the Stage 4 identity seam: the mock user in dev, and the GitHub handle once OAuth lands. A non-operator gets `403 not_operator` before any work runs. The gate is a single middleware/guard on the `/api/admin/*` prefix rather than per-route code, so there is one authorization choke point. The public reads (step 7's Leaderboards view, the environment page) do **not** go through this prefix. They use separate public routes whose board and history reads only ever return `released` iterations. Unreleased results therefore cannot leak through a public endpoint, no matter the caller. A submission-open or play-open iteration can still be a public submit or play target before its results are released.

## Routes

Under `/api/admin/`, attributing actions to the resolved operator identity:

- **Declare**: `POST /api/admin/environments/:envId/iterations`: create an `unreleased`, submission-`closed`, play-`closed` iteration for the environment with an initial config. The config holds an empty or supplied match design, with `deps_version` defaulted to the current template release. Returns the new iteration. Declaring does not auto-close the previous open iteration. Closing and opening are explicit, and the one-open-submission and one-play-open invariants are enforced by their lifecycle routes.
- **Configure**: `PUT /api/admin/iterations/:id/config`: replace the iteration's `IterationConfig` through the typed codec from step 1. The config now includes `deps_version`: the dedicated deps-version route is gone, and the dependency set is just another config value, kept as one set for the whole iteration. The route rejects an unknown key or malformed match design with `400` and a specific reason. It also validates each match's slot count against the environment metadata. Every match must assign at least one slot, cannot exceed the environment's max slots, and cannot fall below its min slots when that metadata is stricter. Empty `matches` is allowed only while the iteration is still unconfigured; triggering a run then rejects it with `409 empty_schedule`. The config is no longer permanently immutable after a run. Instead it is destructive-with-confirmation. The route refuses with `409 iteration_has_runs` if the iteration already has runs, or with `409 iteration_has_submissions` if the edit changes `deps_version` while submissions exist — **unless** the request carries an explicit `force` flag. The console sends `force` after a confirmation dialog that spells out what is destroyed. With `force`, the route deletes the now-invalidated artifacts before applying the edit: the iteration's runs, games, results, and placements when config changes, plus its submissions when `deps_version` changes, since those were built against the old dependency set. A forced edit also clears the per-run `config_snapshot` rows, giving a clean slate to re-trigger. Released iterations can still be unreleased or re-released.
- **Rating prompt**: `PUT /api/admin/iterations/:id/rating-prompt`: set or clear the operator's iteration-wide rating prompt (`setIterationRatingPrompt`, step 1). Unlike config, which includes the deps version, this prompt is editable at any point in the iteration's life — before or after submissions, runs, and release. It is display-only human-feedback guidance and never affects workflow execution. The author's per-submission prompt is a participant action and lives on the public/owner side (step 6), not here.
- **Submission window**: `POST /api/admin/iterations/:id/submissions:open` and `:close`: flip `submission_status`. Opening returns `409 open_iteration_exists` if another iteration for the same environment is already open. Closing gates the form before a final workflow run.
- **Public play window**: `POST /api/admin/iterations/:id/play:open` and `:close`: flip `play_status`. Opening is independent of release status, so an `unreleased` iteration can be opened for play. It returns `409 open_play_iteration_exists` if another iteration for the environment is already play-open. Closing public play stops new public watch/play sessions and rating writes for the iteration, but leaves released boards readable.
- **Release**: `POST /api/admin/iterations/:id/release` and `/unrelease`: flip `release_status`, stamping `released_at` on first release. Release is the explicit operator action that exposes the iteration's results — its boards and history — on the environment page. Unrelease pulls them back to operator-only, which is useful after a bad re-run. Release and unrelease do not touch the play window. An iteration can be play-open while unreleased, and can stay play-open after being unreleased.
- **Trigger / re-run**: `POST /api/admin/iterations/:id/runs`: snapshot the iteration config, deps version, and active `ready` submissions. Build the concrete schedule with step 2's pure scheduler, and reject an empty resolved schedule with `409 empty_schedule`. Then create the `iteration_runs` row and `iteration_run_games` rows in one transaction before handing the run id to the workflow runner (step 4). The route returns the run id immediately and never blocks on containers. A second call is the re-run: it starts a fresh run that replaces the board on completion. The route refuses to start a run when one is already `running` for the iteration (`409 run_in_progress`), so two concurrent runs cannot interleave on the single host. Because the schedule is persisted before enqueue, later resubmissions or validation status changes cannot alter this run.
- **Cancel**: `POST /api/admin/iterations/:id/runs/:runId:cancel`: request cancellation of an in-progress run. The runner stops scheduling further games and marks the run `cancelled` (step 4 owns the cooperative stop).
- **Status**: `GET /api/admin/iterations/:id`: the full admin view. It includes config, all three gates, the latest run with its per-game statuses and any errors, and the computed boards even while `unreleased`. The board portion comes from the `getAutomatedBoard`/`getHumanBoard` computation that lands in steps 5 and 6. Until those land — and until a run has completed — this route returns an empty/absent board. So step 3 ships with the run/status/config fields, and the board fields fill in as steps 5–6 attach. `GET /api/admin/environments/:envId/iterations` lists all iterations, including unreleased ones, for the history/console picker.
- **Log stream**: `GET /api/admin/iterations/:id/runs/:runId/logs/ws`: a WebSocket endpoint matching the app's existing session-streaming transport. It emits the running workflow's per-match container log lines and game-status transitions as they happen. When the run reaches a terminal state, it sends a terminal event and closes. It streams **live only** and reuses the existing transport unchanged. A console attaching mid-run shows progress from the persisted per-game statuses on the status route, then picks up the live log tail from here. **The buffered backlog-on-attach is deferred**, so a late subscriber misses lines emitted before it attached. That is a polish item, not a stage exit criterion. It can be added later as an in-memory per-run buffer in the runner if operators need full mid-run scrollback.

## Public routes

Public board and history reads are separate from `/api/admin/*` and serve only `released` results at the route boundary:

- `GET /api/environments/:envId/iterations`: list released iterations for the environment, newest first, for history links.
- `GET /api/environments/:envId/leaderboards`: return the current released iteration and both boards. Also return the current open submission iteration id and current play-open iteration id when either exists. If nothing is released yet, return an empty current-board payload. The submission and play targets are reported even when their iterations are unreleased, since an open submission or play window makes an iteration publicly reachable without exposing its boards.
- `GET /api/environments/:envId/iterations/:iterationId/leaderboards`: return both boards for a specific released iteration. Return `404` for unreleased or unknown iterations.
- `GET /api/environments/:envId/agents/:ownerId/placements`: return automated placements for the agent profile, including the Naive-free submitted-agent rows only.

## Background execution and the runner seam

Triggering a run must not block the HTTP request on Docker, just as Stage 5's submit route does not block on the validation pipeline. The route snapshots config/deps and the ready-submission roster, persists the resolved game schedule with a `pending` run row, enqueues that run id on the in-process workflow runner (step 4), and returns. The runner drives the persisted games to a terminal state, writing `game_results` and emitting the log events the WebSocket route relays. On backend startup, any run left `running` by a process death is reconciled to `failed`. A partial leaderboard run is not silently resumed; the operator re-runs. This mirrors Stage 5's startup recovery posture but chooses fail-closed for the heavier workflow.

## Tests

Backend Vitest with a fake/stub runner and `:memory:` storage, no Docker:

- Every `/api/admin/*` route returns `403 not_operator` for a non-operator identity and proceeds for an operator. The dev mock user is an operator.
- Declare creates an `unreleased`, submission-`closed`, play-`closed` iteration with the current `deps_version`. Configure round-trips a valid `IterationConfig` and `400`s an invalid one with a specific reason, covering zero slots, environment slot-count mismatch, empty seeds, and non-positive games.
- Updating config after a run returns `409 iteration_has_runs` without `force` and succeeds with `force`, deleting the existing runs/games/results/placements. A forced `deps_version` change deletes the iteration's submissions, while an unforced one returns `409 iteration_has_submissions`. Setting the rating prompt succeeds even after a run exists, since it is never gated by these rules.
- Open/close flips `submission_status`. Opening while another iteration is open for submissions returns `409 open_iteration_exists`. Play-open is allowed on an `unreleased` iteration and conflicts with another play-open iteration via `409 open_play_iteration_exists`. Release/unrelease flips `release_status` and stamps `released_at` once. The public iteration and leaderboard reads never return an `unreleased` iteration's boards.
- Triggering a run snapshots config/deps/requested_by plus the eligible ready submissions, persists the concrete schedule before enqueue, rejects an empty schedule with `409 empty_schedule`, and returns its id without invoking Docker inline (the stubbed runner records the enqueue). A second trigger while a run is `running` returns `409 run_in_progress`. Cancel marks the run `cancelled` through the runner stub.
- The status route returns the admin view, including an unreleased iteration's boards. The list route includes unreleased iterations for operators.
- The public history and leaderboard routes return only released iterations and `404` an unreleased-specific board read.
- The WebSocket log-stream route relays the stub runner's emitted lines to a subscriber and closes on terminal status.
- Startup reconciles a leftover `running` run to `failed`.

The Docker-backed end-to-end of an actual run is covered by step 4. This step's tests use a stub runner, so the routes, gating, and streaming are proven Docker-free.

## Done when

Over HTTP, an operator can do all of the following. Declare and configure a submission-closed, play-closed, unreleased iteration. Explicitly open or close its submissions under the one-open-submission invariant. Release and unrelease it. Open or close public play under the one-play-open invariant. Trigger and re-run its workflow from a trigger-time roster and schedule snapshot — non-blocking, with a `409` against concurrent runs and empty schedules. Inspect its full status. And subscribe to a run's live WebSocket log stream. Public routes expose only released history and boards, and they report separate public targets for submission and play. The runner itself is a stub here; step 4 makes the trigger actually launch containers.
