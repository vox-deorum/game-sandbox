# Stage 6.7: Frontend, Leaderboards and Admin Console

Status: not started.

Part of [Stage 6](../stage-06-leaderboards.md). This is build-order step 7: the user-facing surfaces. It serves two distinct audiences but stays in one subplan, because both share the same API client and design primitives. The first is the **public Leaderboards** view (both boards, history, profile placements, board-row replays). The second is the **operator admin console** (declare/configure/open/close/release, plus trigger/re-run with a live log stream). Both build on the Stage 4.5 design system and vue-router setup (`frontend/src/main.ts`, plain library-mode router).

## Public: Leaderboards on the environment page

Per [frontend.md](../../docs/specs/frontend.md), the environment page shows the two leaderboards for the current iteration side by side, with links to historical iterations.

- **Both boards side by side** for the environment's current **released** iteration. The automated board shows rank, agent, mean normalized score, weighted mean agent compute time as its own column, a failure indicator, and a "Replay" link per row to the Stage 4 replay viewer. The human-feedback board shows rank, agent, mean rating, and count; agents with under three ratings appear unranked. The two boards never merge into one number, mirroring the spec.
- **Separate public targets.** The environment page shows the open submission iteration for the submit form and the current play-open iteration for watch/play, whenever either exists. They may differ, and either may still be unreleased. If submissions are open for an unreleased next round, the form is available without exposing its boards. If no iteration is play-open, the watch/play controls are disabled, but released history stays readable.
- **History.** The page links to historical released iterations; selecting one shows that iteration's boards read-only. A dedicated per-environment, per-iteration **Leaderboards page/route** (the spec's "Leaderboards" page) hosts the full side-by-side view. It is linkable by URL with the iteration id, so a specific iteration's boards are shareable. The environment page embeds the current iteration's boards and links into this page for history.
- **Agent profile placements.** The agent profile page (Stage 5.6) replaces its Stage 6 placeholder with real **leaderboard placements**. For each iteration the agent competed in, it shows the agent's rank, mean score, and mean agent compute time, read from the public placements route (step 3/5). Each placement links to that iteration's Leaderboards view.
- **Board-row replays.** Each automated-board row deep-links the representative recording (step 5) through the existing replay route. This makes the spec's "replays linked from board rows" work against the Stage 4 viewer, with no new player.
- All public board and history reads hit the public (non-`/admin`) routes from step 3. Those routes only return released iterations' boards, so an unreleased iteration's boards never appear here, even when it is a public submit or play target.

This adds a new Leaderboards route to `frontend/src/main.ts` (e.g. `/environments/:envId/leaderboards/:iterationId?`, defaulting to the current released iteration). The renderer/registry imports are unchanged.

## Operator: admin console

A new operator-only console drives the step-3 admin API. The UI gates it by the `me` answer. The app already fetches `GET /api/me` once via `me.ts`; extend it to report `is_operator` from the step-1 predicate. The console route and its nav entry then render only for operators. The backend gate (step 3) is the real authority; the UI gate just avoids showing dead controls.

- **Iteration management.** List the environment's iterations, including unreleased ones, declare a new one, and edit its config. The config covers the **match design** (add match configurations and set each one's slot composition of `builtin-naive`/`submission` seats, seeds, and game count), the `deps_version` (now part of the config, defaulted to the current release), and the override blocks (timeouts active; messaging/LLM fields present but labeled "applies in Stage 8/9"). The match editor will not save a match with zero slots, and it surfaces environment slot-count errors from the API. Two edits prompt a confirmation dialog: editing config when runs exist, and changing `deps_version` when submissions exist. The dialog spells out what will be deleted — the existing runs and boards, plus the submissions on a deps change — and sends the step-3 `force` flag. Without confirmation the edit is refused. Declaring creates an `unreleased`, submission-`closed`, play-`closed` iteration, so the console should make clear to the operator that opening submissions, opening public play, and releasing results are separate actions. This builds on the Stage 4.5 form primitives (`UiField`/`UiInput`/`UiButton`, status badges, dialogs, and existing layout patterns).
- **Lifecycle controls.** Open/close submissions, open/close public play, and release/unrelease are each a clear button reflecting the three independent gates. The current state is shown alongside: a released/unreleased badge, a submissions open/closed badge, and a play open/closed badge. Opening submissions handles `409 open_iteration_exists` with a direct message that another iteration is already accepting submissions. Opening play handles `409 open_play_iteration_exists`, so the operator sees they must close play on another iteration first. Releasing is the action that exposes the boards on the environment page. Opening play is a separate, independent action: it allows public watch/play and rating writes whether or not the iteration is released.
- **Iteration rating prompt.** A small, always-editable text field holds the operator's iteration-wide rating prompt (the step-3 rating-prompt route). It is separate from the match-design config editor because it stays editable after runs and release. The console makes clear that this prompt is shown to human raters for every agent. It is distinct from each author's own per-agent prompt, which is set on the agent profile (step 6).
- **Run controls and live log stream.** Trigger the workflow and re-run it. While a run is in progress, a **live log view** subscribes to the step-3 WebSocket log-stream endpoint, reusing the Stage 3 socket conventions where practical. It shows the per-match container lines and per-game status as they arrive. Opening mid-run renders current progress from the persisted per-game statuses, then tails live log lines. The buffered backlog-on-attach is deferred (step 3/4), so earlier lines are not replayed. A `409 run_in_progress` is surfaced as "a run is already in progress." A `409 empty_schedule` points the operator back to the match design. Cancel is offered for an in-flight run. After completion the console shows the computed boards. An unreleased iteration's boards are visible here before release — this is the verify-before-expose flow.
- **Verify-before-release.** The console renders the unreleased iteration's boards via the admin board read, so the operator inspects the automated and human boards privately, then releases. A re-run recomputes them in place. Release/unrelease controls whether the environment page sees them.

This adds new admin route(s) to `frontend/src/main.ts` (e.g. `/environments/:envId/admin`), rendered only when `me.is_operator` is true. New typed client wrappers live in `frontend/src/api/client.ts`, following the existing wrapper style: for `/api/me`'s `is_operator`, the public board/history/placements endpoints, the rating endpoints, and the admin endpoints.

## Tests

Frontend Vitest (jsdom, mocked fetch), following the Stage 4/5 unit pattern:

- The public Leaderboards view renders both boards from mocked data side by side. It includes weighted mean agent compute time as its own column, the Naive baseline row, a per-row replay link, and the human board's three-ratings ranking with under-threshold agents unranked. An unreleased iteration's boards are never fetched or shown on the public board path.
- The environment page renders separate states for open submissions and open play. It keeps the submit form available for the open submission iteration, disables watch/play when no play-open iteration exists, and lists ready submissions from the selected playable iteration rather than the open submission iteration.
- History links navigate between released iterations, and the Leaderboards route resolves a specific iteration by URL.
- The agent profile shows real placements per iteration linking to the right Leaderboards view (replacing the Stage 5 placeholder).
- The admin console covers the full operator flow. The console route and nav entry render only when `me.is_operator`. Declaring creates a submission-closed, play-closed, unreleased iteration. Editing the match design and deps version prompts the force-confirmation dialog when runs or submissions exist (and sends `force`), and rejects zero-slot match configs. The iteration rating-prompt field saves and stays editable after a run. Opening submissions handles `open_iteration_exists`. Opening play handles `open_play_iteration_exists` and can target an unreleased iteration. The lifecycle and release controls call the right admin endpoints. Triggering a run subscribes to the WebSocket log stream and renders streamed lines. A `409 run_in_progress` surfaces the in-progress message, and `409 empty_schedule` points at match setup. An unreleased iteration's boards render in the console before release.

## Done when

The environment page shows the current released iteration's two boards side by side, with per-row replays, links to historical iterations, and separate submit and play targets. The Leaderboards page is URL-linkable per iteration, and agent profiles show real placements. The operator console lets an operator drive the full competition cycle the stage's "Done when" describes. The operator can declare and configure a submission-closed, play-closed, unreleased iteration's match design, set the iteration's always-editable rating prompt, open/close submissions under the one-open-submission invariant, release/unrelease, and open/close public play under the one-play-open invariant. They can also trigger and re-run the workflow while watching its container logs stream live over WebSocket, inspect the unreleased boards, and release. Non-operators see none of it.
