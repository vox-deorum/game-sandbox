# Stage 6.7: Frontend, Leaderboards and Admin Console

Status: not started.

Part of [Stage 6](../stage-06-leaderboards.md). This is build-order step 7: the user-facing surfaces. Two distinct audiences, one subplan because they share the same API client and design primitives: the **public Leaderboards** view (both boards, history, profile placements, board-row replays) and the **operator admin console** (declare/configure/open/close/release, trigger/re-run with a live log stream). Built on the Stage 4.5 design system and vue-router setup (`frontend/src/main.ts`, plain library-mode router).

## Public: Leaderboards on the environment page

Per [frontend.md](../../docs/specs/frontend.md), the environment page shows the two leaderboards for the current iteration side by side, with links to historical iterations.

- **Both boards side by side** for the environment's current **released** iteration: the automated board (rank, agent, mean normalized score, weighted mean agent compute time as its own column, failure indicator, a "Replay" link per row to the Stage 4 replay viewer) and the human-feedback board (rank, agent, mean rating, count; under-three-ratings agents shown unranked). The two never merge into one number, mirroring the spec.
- **Separate public targets.** The environment page shows the open submission iteration for the submit form and the current play-open iteration for watch/play when either exists. They may differ, and either may still be unreleased. If submissions are open for an unreleased next round, the form is available without exposing its boards. If no iteration is play-open, watch/play controls are disabled while released history remains readable.
- **History.** Links to historical released iterations; selecting one shows that iteration's boards (read-only). A dedicated per-environment, per-iteration **Leaderboards page/route** (the spec's "Leaderboards" page) hosts the full side-by-side view and is linkable by URL with the iteration id, so a specific iteration's boards are shareable. The environment page embeds the current iteration's boards and links into this page for history.
- **Agent profile placements.** The agent profile page (Stage 5.6) replaces its Stage 6 placeholder with real **leaderboard placements**: the agent's rank, mean score, and mean agent compute time per iteration it competed in, read from the public placements route (step 3/5), each linking to that iteration's Leaderboards view.
- **Board-row replays.** Each automated-board row deep-links the representative recording (step 5) through the existing replay route, so the spec's "replays linked from board rows" works against the Stage 4 viewer with no new player.
- All public board and history reads hit the public (non-`/admin`) routes from step 3, which only return released iterations' boards, so an unreleased iteration's boards never appear here even when it is a public submit or play target.

New routes added to `frontend/src/main.ts`: a Leaderboards route (e.g. `/environments/:envId/leaderboards/:iterationId?`, defaulting to the current released iteration). The renderer/registry imports are unchanged.

## Operator: admin console

A new operator-only console driving the step-3 admin API. Gated in the UI by the `me` answer (the app already fetches `GET /api/me` once via `me.ts`; extend it to report `is_operator` from the step-1 predicate) so the console route and its nav entry render only for operators; the backend gate (step 3) is the real authority, the UI gate is just to avoid showing dead controls.

- **Iteration management.** List the environment's iterations (including unreleased ones), declare a new one, edit its pre-run config: the **match design** (add match configurations, set each one's slot composition of `builtin-naive`/`submission` seats, seeds, and game count), the deps_version (defaulted, overridable only before submissions and runs), and the override blocks (timeouts active; messaging/LLM fields present but labeled "applies in Stage 8/9"). The match editor prevents saving a match with zero slots and surfaces environment slot-count errors from the API. Declaring creates an `unreleased`, submission-`closed`, play-`closed` iteration, so the console should show the operator that opening submissions, opening public play, and releasing results are separate actions. Built on the Stage 4.5 form primitives (`UiField`/`UiInput`/`UiButton`, status badges, dialogs, and existing layout patterns).
- **Lifecycle controls.** Open/close submissions, open/close public play, release/unrelease: each a clear button reflecting the three independent gates, with the current state shown (a released/unreleased badge, a submissions open/closed badge, and a play open/closed badge). Opening submissions handles `409 open_iteration_exists` with a direct message that another iteration is already accepting submissions. Opening play handles `409 open_play_iteration_exists`, so the operator sees they must close play on another iteration first. Releasing is the action that exposes the boards on the environment page; opening play is a separate, independent action that allows public watch/play and rating writes whether or not the iteration is released.
- **Iteration rating prompt.** A small always-editable text field for the operator's iteration-wide rating prompt (the step-3 rating-prompt route), separate from the match-design config editor because it stays editable after runs and release. The console makes clear this prompt is shown to human raters for every agent and is distinct from each author's own per-agent prompt (set on the agent profile, step 6).
- **Run controls and live log stream.** Trigger the workflow and re-run it; while a run is in progress, a **live log view** subscribes to the step-3 WebSocket log-stream endpoint (reusing the Stage 3 socket conventions where practical) and shows the per-match container lines and per-game status as they arrive, with the buffered backlog on attach so opening mid-run is not blank. A `409 run_in_progress` is surfaced as "a run is already in progress." A `409 empty_schedule` points the operator back to the match design. Cancel is offered for an in-flight run. After completion the console shows the computed boards (an unreleased iteration's boards are visible here before release, the verify-before-expose flow).
- **Verify-before-release.** The console renders the unreleased iteration's boards (admin board read) so the operator inspects the automated and human boards privately, then releases. A re-run recomputes them in place; release/unrelease controls whether the environment page sees them.

New admin route(s) in `frontend/src/main.ts` (e.g. `/environments/:envId/admin`), rendered only when `me.is_operator` is true. New typed client wrappers for `/api/me`'s `is_operator`, the public board/history/placements endpoints, the rating endpoints, and the admin endpoints live in `frontend/src/api/client.ts`, following the existing wrapper style.

## Tests

Frontend Vitest (jsdom, mocked fetch), following the Stage 4/5 unit pattern:

- The public Leaderboards view renders both boards from mocked data side by side, with weighted mean agent compute time as its own column, the Naive baseline row, a per-row replay link, and the human board's three-ratings ranking with under-threshold agents unranked; an unreleased iteration's boards are never fetched/shown on the public board path.
- The environment page renders separate states for open submissions and open play, keeps the submit form available for the open submission iteration, disables watch/play when no play-open iteration exists, and lists ready submissions from the selected playable iteration rather than the open submission iteration.
- History links navigate between released iterations and the Leaderboards route resolves a specific iteration by URL.
- The agent profile shows real placements per iteration linking to the right Leaderboards view (replacing the Stage 5 placeholder).
- The admin console route and nav entry render only when `me.is_operator`; declaring creates a submission-closed, play-closed, unreleased iteration; editing the match design and deps version handles immutable-after-submission/run conflicts and rejects zero-slot match configs; the iteration rating-prompt field saves and stays editable after a run; opening submissions handles `open_iteration_exists`; opening play handles `open_play_iteration_exists` and can target an unreleased iteration; lifecycle/release controls call the right admin endpoints; triggering a run subscribes to the WebSocket log stream and renders streamed lines plus the backlog; a `409 run_in_progress` surfaces the in-progress message and `409 empty_schedule` points at match setup; an unreleased iteration's boards render in the console before release.

## Done when

The environment page shows the current released iteration's two boards side by side with per-row replays and links to historical iterations, plus separate submit and play targets; the Leaderboards page is URL-linkable per iteration; agent profiles show real placements. The operator console lets an operator declare and configure a submission-closed, play-closed, unreleased iteration's match design, set the iteration's always-editable rating prompt, open/close submissions under the one-open-submission invariant, release/unrelease, open/close public play under the one-play-open invariant, trigger and re-run the workflow while watching its container logs stream live over WebSocket, inspect the unreleased boards, and release, completing the full operator-driven competition cycle the stage's "Done when" describes, with non-operators seeing none of it.
